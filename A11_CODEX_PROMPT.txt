A11 OBJECTIVE

A11 adds no new product features.

Its job is to attack the complete Release A implementation for security, lifecycle, isolation, retry, concurrency, failure-recovery, migration, and usability defects, then fix only real defects discovered.

Treat A0-A10 as a release candidate, not as trusted code simply because existing tests pass.

The output of A11 should be a hardened Release A that can survive deliberate hostile and failure-oriented testing and whose acceptance stories pass end-to-end.

RELEASE A PRODUCT BOUNDARY

Release A includes:
- isolated infrastructure and database foundation
- authentication and membership
- authorization
- BloomOps shell
- Clients
- Services / Departments / assignments
- versioned onboarding templates and deterministic generation
- Client activation and invitation
- Client portal onboarding

If a test reveals a missing product feature rather than a bug in Release A, document it as out of scope instead of implementing it.

PERMANENT INVARIANTS TO PRESERVE

- BloomOps is post-sale only.
- Leadsthatbloom remains separate and untouched.
- One Client may have multiple simultaneous Service Engagements.
- Departments organize work but never grant authorization.
- owner_membership_id is responsibility, never authorization.
- Client assignment grants that Client and its Services.
- Service assignment grants only that Service, not the Client record or siblings.
- Client portal scope comes only from client_contacts.user_id, never email matching.
- Client relationship status, Client health, Service status, onboarding status, and later work statuses are separate facts.
- Activity is append-only.
- No raw platform passwords.
- Template definitions and provenance remain immutable snapshots.
- Existing generated onboarding must not be silently rewritten by later template changes.
- Database constraints remain the final concurrency authority.
- Environments remain isolated.

A11 HARDENING STRATEGY

Do not merely rerun existing tests.

Build adversarial tests around the boundaries that existing code is most likely to get wrong, including ID manipulation, stale sessions, races, partial failures, cross-workspace relationships, hidden/restricted data, retries, and lifecycle divergence.

When a defect is found:
1. reproduce it with a focused failing test first when practical
2. make the smallest clean correction
3. preserve current product semantics
4. add regression coverage
5. run focused and full verification

Do not refactor broadly just because code could look nicer.

REQUIRED SECURITY SCENARIOS

Prove all of these at the domain and HTTP/session layer where applicable:

1. Client A requests Client B resource by changing:
   - client id
   - onboarding item id
   - onboarding instance id
   - invitation id where relevant
   Expected: safe not-found/denied behavior with no existence leak.

2. Client A cannot read:
   - internal onboarding items
   - restricted onboarding items
   - hidden service/template/provenance identifiers
   - internal membership/user ids
   - internal resolution reasons
   - internal activity metadata

3. Client cannot call internal Client/Service/assignment/onboarding-management APIs merely because they can see their portal.

4. Team Member with only a client assignment can access only canonical assigned scope and cannot acquire Owner/Admin/PM-only onboarding management powers.

5. Team Member with only a service assignment cannot access the parent Client record or sibling Service Engagements and cannot use that service scope to acquire client-wide onboarding access.

6. Department membership alone grants nothing.

7. owner_membership_id alone grants nothing.

8. Suspended or removed membership using an already-issued session is refused on the next request.

9. Workspace status becoming inactive invalidates access immediately.

10. Cross-site state-changing requests are refused consistently.

11. Unknown/unsupported authorization actions default deny.

12. Foreign workspace ids cannot be smuggled through request bodies, query strings, or guessed resource ids to alter another workspace.

13. Client invitation acceptance cannot cross-link a contact from another client/workspace, even under same-email edge cases.

14. Activation-managed invitations remain protected from generic resend/revoke/retarget paths.

15. Raw invitation tokens never appear in database rows, API responses, activity metadata, logs, or persisted test fixtures beyond intentional local email capture.

REQUIRED DATA / TENANT ISOLATION SCENARIOS

REQUIRED LIFECYCLE SCENARIOS

Activation:
- Draft -> Onboarding only for first valid activation
- invalid prerequisites write nothing
- repeated activation does not duplicate core rows/events
- later Client lifecycle changes do not cause activation to rewind state

Onboarding:
- first real mutation starts instance exactly once
- Client non-verification item completion is idempotent
- verification-required Client submission remains In Progress until authorized verification
- untouched In Progress is not mistaken for a durable submission
- verify before submission fails safely
- required Completed / Waived / Not Applicable satisfy completion
- submitted-but-unverified required item does not satisfy overall completion
- optional items never block completion
- hidden/internal required items still count toward overall completion even though they do not appear in Client progress
- Client-facing progress denominator does not leak hidden work
- final completion occurs exactly once
- only initial A9 onboarding completion may automatically move a Client still in Onboarding to Active
- Draft/Paused/Completed/Ended/other unexpected Client lifecycle values are never overwritten by onboarding completion
- Service statuses remain unchanged when Client onboarding completes

Invitation/contact:
- resend rotates pending token and old token becomes invalid
- acceptance retry is idempotent
- accepted invitation cannot be reused by a different identity
- generic invitation management cannot corrupt activation-managed invitation state

REQUIRED RETRY / CONCURRENCY SCENARIOS

Attack at least:

- concurrent first activation requests
- activation request racing primary-contact edit
- activation request racing service addition/removal/status change
- concurrent invitation delivery retry
- expired delivery lease recovery
- token rotation racing stale sender finalization
- concurrent invitation acceptance
- concurrent client completion of the same onboarding item
- concurrent submission of the same verification-required item
- submission racing verification
- concurrent verification
- concurrent Waived / Not Applicable attempts
- two final required-item mutations racing onboarding completion
- request retry after response loss / duplicate browser click

For each, prove one durable fact and one semantic event, never duplicate core records or raw unique/check/FK leakage.
