# Quiet prospect sheet saves

The owner reported that every edit felt like reloading the table. The accepted prior build retains its table DOM, but each save starts a blocking sheet fetch and inserts a separate Updating paragraph. [Actual reproduction](before.json) measured a36px table jump, an Updating message and disabled next-field controls during the held refresh.

Direct-cell post-save reconciliation now runs in the background for the same loaded query. The confirmed cell value remains visible; the next dropdown works without waiting for that read. Starting another save invalidates any older read before it can replace the new value. Query changes, explicit refresh and non-direct operations (retry/recovery, bulk/paste and Undo) retain their stale-action guards until canonical rows arrive. Counts, filtered membership, revisions and derived actions continue to reconcile with the canonical sheet. A failed read leaves the confirmed save visible and offers Refresh; denied access still clears the table.

Compact Saving/Saved feedback has reserved toolbar space, and direct saves no longer insert the table-wide Updating paragraph. Canonical compare/write, undo, failures, recovery and workspace rules remain unchanged. The write itself still briefly blocks duplicate writes; this does not implement simultaneous saves or reduce backend round trips.

Outreach remains derived from the same prospect’s canonical contact/reply/interest/conversion/closed records. The dropdown opens event or review actions; choosing an action alone does not record an event or send a message. No Outreach runtime change is included.
