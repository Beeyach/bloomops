# Running a Systems build

Open **Systems**, choose the Project, and use its Milestones, Actions,
Deliverables and Files. The same path works for GHL and Kajabi. Blueprint setup
and work generation are explicit choices; select only the work this build needs.
Include QA, Client Review, Launch and Handoff when they belong to the engagement.

1. Complete the selected build work and perform QA. Systems shows the current
   readable phase, action progress, waiting work and dependency blockers. Open
   the linked Project or Work view to update the canonical records.
2. Move each output Deliverable through **Internal Review** and **Client Review**
   as appropriate. Record requested revisions by returning it to **In Progress**,
   then review again. An authorized internal coordinator records **Approved**
   once approval has actually been obtained. Completing the QA Action does not
   approve an output, and Client Review does not send a request or collect a
   client approval automatically.
3. Coordinate the approved launch using the Launch Action and Milestone. Perform
   any external launch through the separately authorized provider workflow.
   BloomOps records the operational work; changing its status never publishes
   to GHL or Kajabi. Dependencies show outstanding prerequisites, while manual
   status changes remain available to the authorized operator.
4. Prepare the handoff instructions and attach the document through the Project's
   **Files → Upload file** control, choosing the relevant Deliverable under
   **Attach to**. Add a Deliverable if the handoff is a separate client output.
   Include the operating instructions, delegated-access contact and agreed next
   steps. Keep credentials in the appropriate external vault or delegated access
   system.
5. Choose visibility deliberately. Uploads start internal. For client access,
   the Project, attached Deliverable and File must all be client visible, and the
   contact must still have access to the Client. Set a clear client-facing label;
   internal titles, descriptions and Actions stay private. The client uses the
   existing **Your projects** and **Shared files** sections on portal Home.
6. Record **Delivered** when the output has actually been handed over. This is a
   final Deliverable status with a delivery timestamp. Complete Handoff work and
   update the Project separately when its own completion criteria are met.

A lost generation response can be recovered with the saved build request. An
exact retry preserves the live work, later delivery statuses and attached files;
there is no need to generate a replacement build. If a form reports a stale
revision, refresh and inspect the current decision before changing it.
