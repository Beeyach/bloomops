## Outcome and boundaries

An authorized coordinator submits an Ads creative's fixed copy and explicitly selected media for a Client to approve or request changes. The response belongs to exactly one canonical Content approval round and its immutable review revision. Reuse `content_review_revisions`, `content_approval_rounds`, canonical Content stages, Files/R2 and activity. Add relational media evidence, not another approval engine, File family or duplicate upload.

Offer two explicit review scopes: **Copy only** and **Copy and selected media**. Copy only has zero media; its confirmation and Client view say that no files are approved. Copy and selected media includes 1–10 explicitly selected, ready, internal production assets belonging to the exact Content item. No automatic inclusion of every attachment. Selection order is meaningful and fixed in the submitted round. A changed image/video is a new canonical upload and a new round, never a replacement inside existing evidence.

Keep the current 5 MiB per-file upload limit and existing upload protocol. Initial media selection accepts declared JPEG, PNG, GIF, WebP, MP4 and WebM types; filenames alone do not establish type. This is not content scanning, transcoding or a claim about browser codec support. Other files remain working assets and cannot be included as E3 media. Use a protected attachment download as the dependable review path; no inline HTML/SVG, public URL, external embed, new media service or larger/multipart uploads in this slice.

No provider connection, publishing, scheduling, spend, metrics, notification, real client email or production launch. Approved means the Client approved that submitted round; it does not mean the creative is running or accepted by an ad provider. General portal Content/calendar/recordings and Social collection/page behavior remain Social-only. Existing shared Work remains unchanged.

## Authority and explicit sharing

Internal read/history follows current E2B Ads Project/child rules: Owner/Admin broad; PM broad ordinary Project; Team current Client, Service or exact Project assignment. Restricted Project/Content/File requires exact Project assignment for PM/Team. Use live SQL, including with 240+ assignments; department membership, ownership and Action-only scope grant nothing. Minimal Project/Client/Service labels do not grant parent management.

Request and withdrawal retain the existing coordinator roles: Owner, Admin and Project Manager only. Team may perform authorized production work and read authorized history, but cannot submit or withdraw Client approval. Requesting approval additionally requires an ordinary (non-restricted) Ads Project, internal Content visibility, valid Ads fixed flags and internal production state. Selected assets must be internal, ready and `purpose='asset'`; restricted assets cannot be submitted even by Owner/Admin. Keep Content and File visibility internal. The explicit request shares only its immutable snapshot and selected media through round-scoped access. The UI must say this before submission; uploading a working asset never shares it.

A Client needs a current active Client membership and current accepted `client_contacts.user_id` link to the exact Content Client in the same workspace. Also prove exact Content/Ads Project/Service identity, current canonical Ads department, ordinary Project, internal Content visibility and the exact actionable requested round. No email matching, stale actor scope list, Work visibility or requester session grants Client access. The round grant does not expose the Content detail, Project, Service, unselected assets or generic File route. Construct a Client-visible round resource descriptor only after that exact SQL grant; never relabel a raw internal Content/File descriptor to bypass `evaluate`.

Making the Project or Content restricted, changing Ads eligibility, suspending membership, unlinking the contact, withdrawing or resolving the round revokes the next portal list/detail/download/response. For a media round, archiving or restricting any selected File, missing/mismatched manifest identity, or an incomplete manifest also removes portal actionability for the whole round; never silently present a subset to approve. Restoration of current eligibility may restore an otherwise still-requested round, consistent with existing visibility revocation. Withdrawing remains available to a currently authorized internal coordinator even when media is unavailable, so a request is not trapped.

Portal reads/downloads expose only requested rounds. A resolved round disappears from Client navigation/detail/media; only the original responding Client may retry an identical response while still satisfying current contact/parent/visibility/media authority. Do not return snapshot data from that retry. A different responder, decision or feedback conflicts or is unavailable without leaking the previous response. Internal historical media download remains available for retained ready/archived-ready bytes only while current parent and File visibility authorize the actor. Redact inaccessible historical media metadata for internal users too; a receipt is not an access grant.

## Media evidence and storage boundary

E3A defines immutable review scope/count and ordered relational manifest rows containing the canonical File ID, exact Content/revision ownership, original filename/type/size/hash, successful object key/ETag, ready time and selected File revision. The manifest is sealed when its canonical round is inserted; no append, update, delete or replacement afterward. Preserve the successful original R2 object; there is no copy operation or mutable “latest media” pointer. The captured File revision is selection provenance, not a permanent equality requirement after sealing: legitimate visibility/archive changes increment the current File revision. Later reads/responses check stable pinned generation evidence and current authority, fencing storage checks with the newly loaded current revision.

Before submitting or accepting a media round, reauthorize the complete selection and verify each pinned object's existence and metadata with bounded R2 reads. Recheck live SQL and exact File revisions/identity after storage checks and in the committing batch. On download, resolve the round and manifest, fetch the pinned key, check key/size/type/ETag/checksum, verify the actual bounded bytes against SHA-256, and recheck live authority before returning them. Missing/mismatched evidence returns an unavailable result, never replacement bytes, an empty successful response or a successful approval. No key, checksum, ETag, uploader, attempt record or raw File row enters a portal DTO.

R2 and D1 do not form one transaction. Promise current authority and verified evidence at the last check/commit boundary, not a distributed lock against account operators deleting objects afterward. No E3 application path may overwrite/delete a pinned successful object; out-of-band loss fails closed when next checked. Round lists can use bounded D1 metadata without probing every object; a later storage failure must visibly stop the response and offer reload/return-home, without a false success.

Use existing protected response headers and safe filename handling, with private/no-store and nosniff behavior. Do not forward arbitrary object HTTP metadata. GET returns complete bounded attachments; range/inline playback is outside initial scope. Closing a round revokes future requests, not bytes already downloaded.

## Lifecycle, atomicity and retry identity

Ads keeps recording false, internal review true, client approval true and `publishedAt=null`. Idea → Script → Editing → Internal Review and required-context Revision Requested → Editing remain. Only the explicit approval request operation may move Internal Review → Client Review, in the same atomic D1 batch that captures copy/media, inserts the round, increments Content revision once and writes canonical request/stage activity. No generic transition may create Client Review or Approved.

Capture the immutable revision/manifest under the batch lock while Content is in Internal Review, move Content to Client Review before inserting its requested round (the existing freeze then applies), and use a newly generated revision/round identity as the unique commit receipt for dependent statements. Every selected manifest row must be present and current before that move. A failed guard, incomplete selection, collision or later SQL failure must roll back the complete batch: no orphan revision/manifest, stage-only move or activity-only success. E3B must prove this ordering against real D1 rather than assume per-statement returning values create a transaction guard.

While requested, freeze reviewed copy, platforms, date, fixed flags and editorial stage changes. Current visibility and authority stay revocable; changing a selected File's restriction/archive status may revoke sharing. Unselected working uploads do not change the submitted manifest. Resolve the round first, then change Content and write events atomically: Client approval → Approved; Client changes with required 1–2,000-character feedback → Revision Requested; internal withdrawal → Internal Review. Social withdrawal continues to leave Social Content in Client Review. No review evidence is deleted.

Approved Ads copy remains frozen until an explicit required-context revision transition moves it to Revision Requested, then Editing. The historical approved round remains approved; the current creative no longer presents itself as approved after revision. No Scheduled or Published transition in E3.

Ads request input is exactly `requestId`, `expectedRevision`, `reviewScope`, `media`, where each ordered media entry is exactly `{fileId, expectedRevision}`. Scope/count limits apply before storage. IDs use canonical validators; reject duplicates/unknown keys. Social input remains exactly its existing shape. Retry identity includes requester, Content request revision, scope and ordered File IDs/revisions. A reused request ID with different input conflicts; an exact authorized retry returns only the original round receipt and does not capture changed copy/media. Never trust caller-supplied snapshot fields, keys, hashes, stage or identity. Response and withdrawal keep canonical input limits and exact-round completion/revision receipts.
