## Binding Architecture

D1 follows `docs/RELEASE_D.md`:

- a Systems build is represented by a canonical Project under a Systems Service Engagement
- Project remains the lifecycle/status/health source
- Milestones remain phase/progress records
- Actions remain internal work/dependencies
- Deliverables remain client outputs
- Files remain the shared File/R2 system
- Service/Client/Project assignments remain scope
- Department is organizational only and is never an authorization grant

Do not introduce `systems_status`, `systems_tasks`, duplicate deliverables, duplicate activity, duplicate project assignments, duplicate Files, or another project engine.

## D1 Owns

### Real Systems destination

Replace `app/(internal)/systems/page.jsx` placeholder behavior with a useful Systems operating page built from current database truth.

The page should help an authorized internal user answer:

- Which Systems Clients/Services have active work?
- Which Systems Projects need attention?
- What is in progress, waiting, blocked or review?
- What client-facing Systems Deliverables are upcoming or in review?
- Where should I click to continue the canonical Project or Action work?

Prefer a calm operational hierarchy over a generic metric dashboard.

### Systems eligibility

Systems records must be selected through canonical relational Service Type -> Department relationships and the existing Project -> Service Engagement relationship.

A Project belongs in the Systems specialist destination when its linked Service Engagement is a Systems service according to current canonical relational data.

Do not infer Systems membership from Project name, Service display text or hardcoded GHL/Kajabi string matching when the relational department fact is available.

A Client-level Project without a Service Engagement is not automatically a Systems Project in D1.

### Internal read model

Create or reuse a bounded read-model helper for the Systems destination.

Useful project-row information may include, only where already canonical and readable:

- Project id/name/status/health/target date
- Client name
- Service Type or Service Engagement display context
- readable Milestone progress
- readable open Action summary
- readable Deliverable summary, especially Internal Review / Client Review / Approved / upcoming delivery
- current waiting/blocked/review signal derived from canonical records

Do not store any of these summaries.

Do not let hidden/restricted children affect a user's visible counts, progress, attention reason, ordering or empty-state decisions.

### Filters and bounds

Support only filters that materially help Systems coordination and can be implemented from canonical fields without new specialist state.

Expected useful filters are:

- Client
- Service
- Project status

A platform filter such as GHL/Kajabi is not required in D1 unless repository evidence already provides a canonical platform fact. Do not infer platform from labels just to add a filter.

All queries must be bounded, deterministic and safe under realistic multi-Client assignment scope. Avoid large in-memory ID lists and bind-heavy authorization patterns when current relational predicates can be reused.

### Entry to canonical work

Systems is a specialist view, not a second editor.

Rows and actions should route to existing canonical Project/Action surfaces where management already exists.

If D1 adds a convenient 'New Systems Project' entry, it must reuse the existing Project creation operation and only offer current readable Service Engagements whose Service Type belongs to Systems. Do not fork Project creation behavior or lifecycle validation.

If reusing Project creation cleanly would require a significant unrelated refactor, omit the new-project shortcut in D1 and provide a clear link to the canonical Work/Project creation surface instead.

### Navigation

Keep Systems in the existing internal navigation.

Do not add Client portal Systems navigation.

Do not expose an empty fake module to roles that cannot read any Systems work if current shell/navigation patterns support a safe conditional presentation. However, internal Owner/Admin/PM users may still need the destination as an operational entry point even when no Systems Project currently exists. Choose behavior consistent with the current internal-shell conventions and document it.

## Authorization

Preserve `Identity -> active Membership -> Workspace -> Role -> Scope -> Visibility`.

D1 must reuse current Project/Milestone/Action/Deliverable/File authorization semantics.

Prove at minimum:

- Owner/Admin see authorized Systems work according to current canonical rules
- Project Manager behavior follows current scope/restricted rules
- Team Member only sees Systems records reachable through existing Client/Service/Project/Action assignment semantics
- Department membership alone grants nothing
- Project ownership alone grants nothing
- Action-only scope does not inflate parent Project or sibling child summaries beyond what B3/B6 already allow
- suspended/removed membership revokes access on the next request
- Service reassignment or Project restriction immediately changes the Systems projection
- foreign workspace and foreign Client ids cannot affect filters or results

Do not reveal existence through counts, filters, errors or overflow metadata where existing security conventions avoid it.

## D1 Schema Rule

D1 is expected to be schema-free.

Do not add a Systems table merely to mark a Project as Systems. The current Service Engagement and Service Type Department relationship should own that fact.

A migration is allowed only if inspection proves a concrete D1 requirement cannot be represented safely using current relational truth. If that happens, document the exact blocker before adding the smallest possible structure and do not create future D2-D5 fields preemptively.

Do not modify prior migrations.
