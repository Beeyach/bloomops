# A2 — Database Foundation

## Objective

Introduce the first BloomOps domain schema and migration discipline.

Read `docs/DOMAIN_MODEL.md` before implementation.

## Intended Stack

Use Drizzle for new BloomOps domain schema on D1.

Inherited direct SQL may remain temporarily for inherited generic functionality until its own migration phase.

## Release A Tables

Create only what Release A needs.

Expected concepts:

- workspaces
- authentication tables required by the chosen auth integration
- workspace_memberships
- workspace_invitations
- departments
- department_memberships
- member_capabilities
- clients
- client_contacts
- client_assignments
- service_types
- service_engagements
- service_assignments
- onboarding_instances
- onboarding_items
- templates
- template_versions
- activity_events

Do not pre-create later-release operational tables unless a concrete technical dependency requires them.

Not yet:

- projects
- milestones
- tasks
- content_items
- approvals
- campaigns
- finance_records

## Rules

- migrations own schema changes
- fresh DB must migrate from zero
- no runtime table creation
- no manual production schema drift
- business records use workspace scope where appropriate
- important operational state should not be buried in opaque JSON
- JSON is acceptable for immutable/versioned template definitions where relational querying is not needed

## Verification

- fresh local DB migrates from zero
- fresh staging DB migrates from zero
- migration behavior is deterministic
- schema tests pass
- workspace isolation is represented correctly
- old prospecting tables are not required for new BloomOps domain functions

## Scope Boundary

Do not build auth UI, Clients UI, or Onboarding UI in A2.
