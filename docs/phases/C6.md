# C6 - Client Content Portal

## Objective

Add the general Client Content portal on top of the closed C1-C5 Social system. C6 exposes only safe, relevant, explicitly client-visible Content through the existing Client portal while preserving all current C1-C5 authorization, pipeline, File, recording and approval semantics.

C6 must not create a second Content model, second Client-visibility authority, second approval flow, second File system, or second recording flow. It is a Client-safe projection and interaction layer over the canonical Release C facts that already exist.

## Canonical Client Eligibility

C6 must reuse the current C1-C5 Client access and visibility authority. Do not invent a parallel definition of "client-visible".

A Client-facing Content record is readable only when current database truth proves all required conditions, including the existing canonical equivalents of:

- active authenticated Client membership in the active workspace
- current `client_contacts.user_id` linkage to the exact Client
- Content belongs to that exact workspace and Client
- optional service binding remains canonical for that same Client when present
- Content is currently eligible for Client visibility under the existing C1 visibility rules
- any narrower C4/C5 action-specific conditions remain satisfied before those actions are offered or accepted

Revocation is live. If membership, contact linkage, workspace state, Content visibility, parent scope, service relationship or any canonical authorization fact changes while a session remains issued, the Client must lose access immediately on the next read/write check.

Never rely on navigation hiding or browser state as authorization.

## Conditional Content Navigation

The Client portal has conditional destinations. C6 adds `Content` only when it is meaningful for the current Client.

The Content navigation destination should appear when the current Client has at least one currently readable Content Item that C6 is allowed to expose. Hidden or unauthorized rows must not make the destination appear.

If the current Client has no eligible Content, do not show an empty global Content module merely because the workspace supports Social internally.

Preserve the existing no-client / disabled-client-access behavior inherited from C1 and the existing portal shell behavior from Release B/C.

Do not show hidden counts such as "3 more" based on rows filtered out by authorization.

## Client Content List

Provide a calm, bounded list of the current Client's safe Content work.

The list should answer, without internal operational detail:

- what content is currently in progress
- what is coming next
- what needs the Client's action
- what was recently completed/published

Use only canonical Content facts and deterministic ordering. Prefer existing target publish date, stage, platform and Content identity facts rather than adding duplicate schedule/status state.

The list must be bounded at the SQL/projection layer. Filtering for authorization and eligibility must happen before limits/counts that affect the Client-visible result.

Safe list fields should be the minimum useful allowlist supported by existing product facts, such as:

- Content id as an opaque route identity where needed
- title
- Content type
- safe current status label derived from canonical stage
- target publish date when safe and present
- safe platform labels
- whether a recording action is currently required
- whether an approval action is currently required
- whether safe Client-visible files are available

Do not expose internal owner, assignment, pillar, revision/CAS, internal stage context, staff notes, audit/activity internals, service IDs, membership IDs, storage keys, upload internals, request keys or hidden counts.

## Client-Safe Status

C6 may translate canonical pipeline stages into calm Client-facing labels, but it must not create a second mutable status field.

Any Client-facing label must be a pure projection of canonical Content stage/current facts.

Avoid exposing internal workflow detail that is not useful to the Client. If exact stage names are already considered safe in existing product wording, reuse them consistently. Otherwise map them through one allowlisted presentation helper with tests.

Required-action state is separate from generic status. Approval and recording eligibility must continue to come from the exact C4/C5 rules rather than from label text.

## Content Detail

If the existing application structure makes a detail route the cleanest way to present Content, C6 may add one narrow Client Content detail route.

The detail surface must use an exact Client DTO and may include only information that is currently safe and useful, for example:

- title
- Content type
- Client-safe status
- target publish date
- platforms
- current required action entry points
- Client-visible Files/assets
- limited safe published/recent-result facts if already canonical

C6 must not expose the live internal editing payload or simply serialize a Content row.

Private script, hook, caption, CTA or other editorial fields are not generally exposed by C6 merely because C5 approval snapshots can contain them. C5's immutable approval snapshot is a separate, explicit review package. General Content visibility does not automatically grant access to every reviewed or internal copy field.

If a Client needs to see review copy, reuse the existing C5 approval route/snapshot authority for that specific requested round.

## Existing Approval Actions

C6 must preserve C5 as the sole formal approval/revision authority.

When an eligible Content Item has a current Requested approval round, C6 may surface an "Approval needed" action from the Content list/detail. The action must lead to or reuse the existing C5 Client approval surface and endpoint rather than implementing a second approval mutation.

Preserve all C5 guarantees, including:

- immutable review snapshot
- append-only rounds
- exact current authorization
- Requested-round checks
- response/withdraw races
- safe bounded feedback
- idempotent/retry behavior
- no generic Client stage transitions

C6 presentation must not expose completed approval history beyond what the C6 contract explicitly allows. General approval history remains an internal/C5 concern unless exact existing Client product behavior already exposes a safe subset.

## Existing Recording Actions

C6 must preserve C4 as the sole recording upload authority.

When a Content Item is currently eligible for Client recording upload, C6 may surface a "Recording needed" action from the Content list/detail. The action must lead to or reuse the existing C4 recording route and endpoint rather than creating a second upload path.

Preserve all C4 guarantees, including:

- exact Client/Content eligibility
- private R2 storage
- current contact/visibility checks
- retry/recovery rules
- File lifetime and size limits
- no Client-selected visibility/purpose/storage authority

C6 must not make a recording route reachable merely because a Content card exists. C4 action-specific authorization remains authoritative.

## Client-Visible Content Files

C6 may expose safe Content Files/assets only through the existing C4 File metadata and private R2 system.

A File is Client-readable in C6 only when the existing File/Content authority says it is currently visible to that Client. Reuse the canonical File visibility and download authorization helpers or extract shared helpers without changing their semantics.

Client File DTOs must be exact and minimal. Reuse existing safe fields where possible, such as:

- id
- filename
- MIME type
- byte size
- ready/status facts needed for presentation
- ready timestamp when already safe

Never expose:

- R2 keys
- bucket/binding names
- hashes/checksums unless already intentionally Client-visible
- uploader internals
- recovery generations
- request keys
- internal visibility controls
- storage/provider metadata
- hidden File counts

Only Ready Files may download unless C4 already defines a narrower retry case for the uploader. C6 must not broaden that exception.

C5 review snapshots intentionally exclude Files. C6 must not retroactively put mutable File state into historical approval snapshots.

## Upcoming Work and Recent Results

C6 should organize safe Content into a simple Client-oriented experience instead of reproducing the internal Social pipeline dashboard.

At minimum, make current/upcoming work understandable using canonical stage/date facts.

Recent results may include recently Published Content only when repository evidence provides safe canonical facts. Do not invent performance metrics, provider publication records or analytics tables. If no safe result metric exists, "recent results" can be satisfied by a bounded recent-published presentation rather than fabricated analytics.

Do not create a duplicate calendar or result state table.

## DTO and HTTP Safety

Every C6 Client read must use a dedicated exact allowlist. Do not return internal domain objects and strip fields in the browser.

Follow current repository conventions for:

- authorization before sensitive input-dependent work where applicable
- exact query/body validation
- `no-store` / non-cacheable private responses
- safe sanitized errors
- same-origin / Origin controls where applicable
- bounded pagination/list sizes
- deterministic sorting
- current database truth on each request

Cross-client and hidden records should resolve through the repository's established safe not-found/forbidden behavior without confirming hidden record existence.

## Hidden-Count and Enumeration Safety

C6 must prove that unauthorized or hidden Content and Files cannot influence Client-visible counts, empty states, overflow indicators, pagination metadata or navigation eligibility.

Do not:

- fetch 200 raw rows then filter in JavaScript and tell the Client there are more
- count all Content then subtract hidden rows
- expose total internal File counts
- reveal another Client's opaque ids through pagination or errors

Eligibility must be expressed as close to the bounded query/projection as the current architecture safely allows.

## Internal Surfaces

C6 should make the smallest internal changes necessary for shared projection/helper reuse.

Do not redesign staff Social pages, Content forms, pipeline controls, approval history, recording management or calendar views.

If a shared helper is extracted, prove internal behavior is unchanged with regression tests.

## Required Tests

Add focused tests that prove C6 correctness, not merely rendering.

At minimum cover:

### Authorization and tenant isolation

- Client A cannot read Client B Content by direct route/API id
- Client A cannot read Client B Content Files
- hidden/internal Content cannot be retrieved directly
- internal-only Files cannot be retrieved directly
- current contact revocation removes C6 access
- membership/workspace revocation removes C6 access
- visibility revocation removes C6 access
- optional service/parent invalidation removes access where canonical rules require it

### Navigation and projection

- Content nav appears only for a Client with at least one eligible Content Item
- hidden rows do not make Content nav appear
- no-client / disabled-client-access behavior remains unchanged
- list bounds happen after eligibility, with no hidden-count/overflow leakage
- ordering is deterministic
- DTO contains only the exact allowlist
- internal fields never appear in serialized responses

### Existing C4 recording behavior

- eligible recording action is surfaced correctly
- ineligible recording action is absent
- direct recording endpoint still enforces C4 rules
- C6 does not create duplicate upload state

### Existing C5 approval behavior

- Requested approval action is surfaced correctly
- completed/withdrawn/ineligible approval action is absent as required
- direct approval endpoint still enforces C5 rules
- C6 does not duplicate or bypass approval transitions

### Files

- only currently Client-visible eligible Content Files appear
- only authorized Ready downloads succeed under existing C4 rules
- hidden File rows do not affect visible counts/empty state
- storage internals never appear

### Regression

- focused C1-C5 Content suites remain green
- Release B portal/File regressions remain green where touched
- existing `/portal/recordings/...` behavior remains green
- existing `/portal/approvals/...` behavior remains green
- internal Social views remain unchanged where shared helpers are refactored

### Browser acceptance

Exercise the integrated Client story at the existing representative widths, including at least:

- Social-only Client with Content nav
- non-Social/irrelevant Client without Content nav
- multi-service Client where other portal destinations remain intact
- upcoming Content
- recording-needed Content
- approval-needed Content
- Client-visible File download entry
- recently Published Content
- empty/no-action state
- long text/filename layout
- keyboard focus
- mobile touch targets
- current revocation causing previously visible Content to disappear or become inaccessible

Use synthetic/local data only. Do not write staging or production business data.
