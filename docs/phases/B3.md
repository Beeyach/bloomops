## Canonical Action Model

UI terminology is always **Action**. The physical table may be `actions` or another non-conflicting name if repository preflight finds an inherited-table collision, but do not expose `task` terminology in the UI merely because the durable domain document says the database may use `tasks`.

For B3, every Action belongs to exactly one workspace and one Project. Client, Service Engagement, and Department context derive from that Project rather than being stored as independent competing facts.

A Milestone is optional. If present, it must belong to the same workspace and Project as the Action.

Canonical fields should include the smallest coherent set of:

- id
- workspace
- Project
- optional Milestone
- title
- optional description
- status
- priority
- optional assignee membership
- optional due date
- waiting type
- waiting explanation
- internal visibility
- revision/concurrency token
- retry metadata for safe creation if the existing B2 request-key pattern remains the best fit
- server-owned completion timestamp for Done
- created/updated timestamps

Do not duplicate Client, Service, Department, Project status, Milestone status, or any other parent lifecycle fact onto the Action.

The title is required and bounded. Description is optional and bounded. Due date must be a valid calendar date. Assignment must point to an active internal workspace membership at the moment it is created or changed. A later inactive assignee may remain as historical responsibility until deliberately reassigned, but it must grant no live authorization.

Actions are internal work in Release B. B3 must not expose Actions to the Client portal. If the implementation reuses a shared visibility vocabulary, application and database rules must still prevent a client-visible Action state. Internal and restricted are the only meaningful Action visibility modes in B3.

## Priority

Use one bounded priority vocabulary. If no stronger repository source already defines one, use:

- Low
- Normal
- High
- Urgent

Default is Normal.

Priority is a sorting/filtering fact only. It must not silently alter lifecycle, due date, assignment, or dependency state.

## Lifecycle

Canonical B3 states are:

- To Do
- In Progress
- Waiting
- Review
- Done
- Cancelled

Use an explicit transition matrix rather than arbitrary request-body writes. Unless repository evidence requires a narrower coherent matrix, use:

| From | Allowed next states |
|---|---|
| To Do | In Progress, Waiting, Cancelled |
| In Progress | Waiting, Review, Done, Cancelled |
| Waiting | In Progress, Review, Done, Cancelled |
| Review | In Progress, Done, Cancelled |
| Done | None |
| Cancelled | None |

Every Action starts To Do. Done and Cancelled are terminal in B3.

Entering Done records one server-owned completion timestamp. Cancelled has no completion timestamp. Identical retries are no-ops. Competing stale writes conflict rather than silently overwrite.

Action lifecycle must never mutate Project status/health, Milestone status, Client relationship/health, Service lifecycle, Onboarding, Department membership, or another Action's status.

## Waiting Semantics

Waiting uses the durable domain vocabulary:

- Client
- Ellen
- Ary
- Team
- External
- Dependency
- Other

When an Action is explicitly in Waiting, store both a waiting type and a bounded human explanation of what or whom it is waiting on. Ordinary multiline text is allowed. Leaving Waiting clears both waiting fields.

Dependency blocking is also derivable from dependency edges. Do not automatically rewrite an Action's lifecycle merely because a prerequisite becomes incomplete or complete.

An Action can therefore be:

- lifecycle status Waiting because a human deliberately put it there
- dependency-blocked because an unfinished prerequisite exists
- both at the same time

Those are separate facts.

## Assignment and Authorization

Preserve `Identity -> Role -> Scope -> Visibility`.

Coordinator behavior:

- Owner/Admin/Project Manager may create, edit, assign, reprioritize, set due dates, transition, and manage dependencies for Actions inside Projects they may manage.
- Department membership alone grants nothing.
- Project ownership alone grants nothing.

Team Member behavior:

- A Team Member may read Actions inside Projects already in scope through existing Client, Service, or explicit Project assignment rules.
- Being the Action assignee may additionally grant access to that Action only, with the minimum parent labels/context required to understand the work. It must not grant the parent Client, Service, full Project, sibling Milestones, or sibling Actions.
- A Team Member may progress only an Action currently assigned to their own active membership.
- Team Member progress authority is limited to lifecycle transitions and Waiting context required by that transition. Team Members do not create Actions, reassign them, change priority/dates/structural details, manage dependencies, or expand visibility.
- If an Action is reassigned away, the old assignee loses that Action-only scope immediately unless another canonical scope rule still grants it.
- An inactive assignee grants nothing.

Restricted Actions:

- Owner/Admin may read/manage.
- Project Manager requires the same explicit Project assignment rule used by B1/B2 restricted work unless already allowed by a narrower canonical rule.
- Team Member requires either their own current Action assignment or the explicit Project assignment needed by restricted parent work.
- Client never reads Actions.

All read and write paths must recheck current membership, workspace, scope, assignment, parent visibility, and Action visibility against the live database rather than trusting a stale actor object.

## Dependencies

Use a simple directed edge table conceptually equivalent to `task_dependencies`:

- action_id
- depends_on_action_id

B3 dependency rules:

- both endpoints belong to the same workspace
- both endpoints belong to the same Project
- an Action cannot depend on itself
- duplicate edges are impossible
- adding an edge that would create any directed cycle is refused atomically
- guessed, foreign, hidden, or cross-Project endpoints fail without leaking existence
- removing an edge is safe and idempotent
- dependency changes do not mutate Action lifecycle automatically

Cycle prevention must be proven against more than the two-node case. Include long chains, diamond graphs, attempted back-edges, concurrent competing edge creation, and stale scope changes.

Prefer a database-backed recursive reachability check under the committing write lock or an equivalently strong design. A preflight-only in-memory graph check is insufficient if two concurrent requests can both pass and create a cycle.

## Dependency Blocking

An Action is dependency-blocked when at least one direct prerequisite is not in a terminal satisfying state.

For B3, Done satisfies a prerequisite. Cancelled does not satisfy it unless repository evidence gives a stronger canonical rule. If a prerequisite is Cancelled, surface that dependency as unresolved rather than pretending the downstream Action is clear.

Do not persist a second `blocked` status merely to represent this projection.

The Action read model may include derived fields such as:

- `dependencyBlocked`
- count of unresolved prerequisites
- safe prerequisite labels for authorized internal users

These are projections from canonical Action/dependency rows.

## Overdue Semantics

Ordinary overdue means:

- due date is before the relevant current calendar date
- Action is not Done or Cancelled
- Action is not dependency-blocked

A downstream Action blocked by an unfinished prerequisite must not appear as ordinary overdue work merely because its own due date passed.

The UI may separately label it as blocked by dependency. Do not silently change due dates.

Tests must freeze or explicitly supply time so timezone/date behavior is deterministic. Reuse the existing workspace/client timezone conventions where available rather than inventing a new global timezone fact.

## Activity

Record significant changes in canonical `activity_events` with `subject_type='action'`, Action subject ID, and Client/Service context derived from the parent Project.

At minimum distinguish:

- Action created
- details changed
- assignment changed
- priority changed if not covered coherently by details
- status changed
- dependency added
- dependency removed

Events must commit atomically with the fact they describe. Retries and concurrent losers append no semantic history. A late activity failure rolls back the mutation.

Any Project or Client history projection that includes Action events must filter by the Action's **current** readable scope/visibility so historical titles do not leak after restriction, reassignment, or scope revocation.

Clients receive no Action activity in B3.

Dependency activity must not serialize hidden sibling titles or a complete dependency graph to an actor who cannot currently read those Actions.

## Internal Work UI

B3 should make the Work area feel like an actual day-to-day operations surface.

Implement functional Action views consistent with `PRODUCT_SPEC.md`:

- Mine
- Today
- Upcoming
- Waiting
- Review
- Overdue
- All

These views are projections over canonical Action rows, not duplicate status tables.

Filters should support the B3-ready subset of:

- Client
- Department
- Service
- Project
- Assignee
- Status
- Priority

Do not fabricate later specialist data to satisfy a filter. Context such as Client/Service/Department may be derived through Project joins.

At minimum, list rows should make title, Client/Project context, assignee, status, priority, due date, and dependency-blocked state understandable without card-grid clutter.

`Mine` means actions assigned to the current actor. Coordinator roles may still use the other views across their allowed scope.

Today/Upcoming/Overdue must use deterministic server-side date logic. Waiting should use explicit Waiting lifecycle. Review should use Review lifecycle. Dependency-blocked work may appear in Mine/All/Today/Upcoming as appropriate but must not be counted as ordinary Overdue.

Keep result sets bounded with clear filtering/pagination/overflow behavior. Do not solve D1 parameter limits by expanding thousands of bound IDs; use relational predicates/joins as B1/B2 already do.

## API Boundary

Follow A11/B1/B2 API hardening:

- real session identity
- origin protection on mutations
- strict object JSON parsing
- exact body allowlists
- safe 400/403/404/409/500 responses

There are no Client portal Action routes in B3.

Test at minimum:

- Workspace A cannot read or mutate Workspace B Actions/dependencies
- Client A cannot read any Action, including guessed own-Project IDs
- Team Member with no canonical scope and no Action assignment sees nothing
- Department membership alone grants nothing
- Project owner grants nothing
- explicit Project assignment grants only that Project tree
- Action assignment grants only that Action and minimal context, not parent/sibling scope
- reassignment revokes old Action-only scope immediately
- inactive assignee grants nothing
- restricted rules hold for PM and Team Member
- Milestone linkage cannot point outside the Action's Project
- lifecycle refuses invalid transitions
- Waiting requires valid type plus bounded explanation
- identical create/detail/status retries do not duplicate facts/history
- competing stale mutations conflict
- late activity failure rolls back Action/dependency mutation
- dependency self-edge/duplicate/cross-Project/foreign endpoints are refused
- cycles of length 2 and longer are prevented
- concurrent dependency additions cannot create a cycle
- dependency removal is idempotent
- unresolved prerequisite projection updates immediately after prerequisite status changes

- malformed/non-object JSON is safe 400

## Acceptance Story

Prove at least one end-to-end B3 story over the real local Worker/database:

1. A coordinator opens an existing B2 Project and creates several Actions, with some attached to Milestones.
2. Actions are assigned, prioritized, dated, and moved through valid states without changing Project/Milestone lifecycle.
3. A Team Member sees an assigned Action, can progress only that assigned Action, and does not gain the parent Client/Service/Project or sibling work merely from assignment.
4. The coordinator creates a dependency chain and the downstream Action becomes dependency-blocked without changing its lifecycle status.
5. Attempting a back-edge that would create a cycle fails atomically.
6. The blocked downstream Action is not treated as ordinary overdue while its prerequisite is unfinished.
7. Completing the prerequisite immediately clears the derived dependency block; the downstream Action can then become ordinary overdue if its due date is already past.
8. Reassignment/restriction/suspension revokes stale access immediately without leaking historical Action names.
9. A Client session cannot read Actions or Action activity at all.
