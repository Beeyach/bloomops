# B4 - Deliverables

## Objective

Add Deliverables as the client-receivable output layer inside Projects, separate from internal Actions. B4 starts only after B3 Actions + Dependencies is merged and both post-merge gates are green on the actual B3 merge SHA.

## B4 Owns

- additive Deliverable relational schema and migration
- Deliverable lifecycle and validation
- Project-scoped Deliverable creation/editing
- explicit Client visibility and safe portal projection
- internal/client review-state foundation without inventing approvals history yet
- significant immutable Deliverable activity
- Project detail integration
- client-facing Deliverable summaries where explicitly visible
- retry/concurrency behavior for create/edit/status mutations
- tenant/scope/visibility/migration/Worker/browser verification

## B4 Does Not Own

- Files/assets/uploads
- versions
- formal approval rounds/history
- comments
- notifications
- templates or automatic Deliverable generation
- automatic Project/Action/Milestone lifecycle transitions
- Social/Ads/Systems specialist pipelines
- Home dashboard composition
- B5+ work

Do not create placeholder tables, routes, tabs, counters, or fake UI for later phases.

## Canonical Deliverable Model

A Deliverable belongs to exactly one workspace and one Project. Client, Service and Department context derive from the Project rather than being duplicated.

Canonical states:

- Planned
- In Progress
- Internal Review
- Client Review
- Approved
- Delivered
- Cancelled

Use the smallest coherent fields needed for B4:

- id
- workspace
- Project
- internal title/name
- optional client-facing label
- optional description
- status
- explicit visibility
- optional target date
- server-owned delivered/completed timestamp where appropriate
- revision/concurrency token
- retry metadata for safe create
- created/updated timestamps

Deliverables are not Actions. Action assignment, due-date semantics, dependencies and internal work lifecycle must remain independent.

## Lifecycle

Use an explicit transition matrix rather than arbitrary status writes. Unless repository evidence requires a narrower coherent matrix:

| From | Allowed next states |
|---|---|
| Planned | In Progress, Cancelled |
| In Progress | Internal Review, Cancelled |
| Internal Review | In Progress, Client Review, Approved, Cancelled |
| Client Review | In Progress, Approved, Cancelled |
| Approved | Delivered, Cancelled |
| Delivered | None |
| Cancelled | None |

Every Deliverable starts Planned. Delivered and Cancelled are terminal in B4. Delivered records one server-owned timestamp. Identical retries are no-ops; stale competing writes conflict.

No Deliverable transition may silently mutate Project, Milestone, Action, Client, Service or Onboarding lifecycle.

## Authorization and Visibility

Preserve Identity -> Role -> Scope -> Visibility.

- Owner/Admin/Project Manager coordinate Deliverables for Projects they may manage.
- Team Member is read-only in B4 unless repository evidence requires a narrower existing rule. Deliverable assignment is not introduced.
- Department membership and Project ownership grant nothing.
- Project scope and visibility cap Deliverable scope.
- Restricted Deliverables follow the same explicit Project-assignment restriction pattern used by B1/B2/B3.
- Clients see only Deliverables under their own currently linked Client, only when the parent Project is client-visible and the Deliverable itself is client-visible.
- Clients never receive internal title/description, revision, activity, identities, Service/Department IDs, or hidden counts through the portal projection.

## Client Projection

Use a dedicated allowlist. A safe B4 Client DTO should expose only what the Client needs, such as:

- id
- label
- statusLabel
- targetDate
- deliveredAt

Do not serialize raw Deliverable rows.

If zero visible Deliverables exist, omit the portal section rather than rendering fake progress or an empty module.

## Activity

Record significant Deliverable changes in canonical activity_events with subject_type='deliverable' and Client/Service context derived from Project.

At minimum distinguish:

- Deliverable created
- details changed
- status changed
- visibility changed if not coherently covered by details

Activity commits atomically with the fact. Retries and losers append no duplicate semantic history. Project/Client history must filter Deliverable events by current scope/visibility so old titles do not leak after restriction. Clients receive no internal Deliverable activity in B4.

## UI

Integrate Deliverables into existing Project detail. Internal UI should support create, edit, explicit status controls, visibility, target date, and a clear separation from Actions.

The portal may show visible Deliverables under visible Projects, using safe labels and plain language. Do not add Files/version/approval controls yet.

## API and Security

Follow A11/B1/B2/B3 hardening:

- real session identity
- Origin protection on mutations
- strict object JSON
- exact body allowlists
- safe 400/403/404/409/500
- no raw SQL/constraints/stacks
- no-store on protected responses
- guessed/foreign IDs fail without leaking existence
- live membership/scope/visibility rechecks inside committing writes

## Migration Safety

Use an additive migration after B3, expected as 0011_b4_deliverables.sql unless the migration journal requires another exact name. Do not rebuild Release A/B1/B2/B3 tables.

Preserve automatic zero-to-current triggering for schema/Drizzle changes and the existing disposable-target safety model.

## Acceptance Story

Prove at least one end-to-end B4 story:

1. Coordinator creates multiple Deliverables in an existing B3 Project.
2. Deliverables move through valid lifecycle states without changing Project/Milestone/Action state.
3. Restricted/hidden Deliverables remain hidden from unauthorized Team/PM actors and historical projections.
4. Client sees only explicitly visible Deliverables under an explicitly visible Project, with exact allowlisted fields.
5. Hiding/restricting a Deliverable removes it immediately from Client projection without hidden counts/history leakage.
6. Retries/concurrency/failure rollback preserve one fact plus one semantic event.

## Exit Criteria

B4 is complete only when Deliverable schema, lifecycle, visibility, Project integration, Client projection, activity, concurrency and isolation are coherent; all prior regressions remain green; migration/Worker/browser gates pass; docs are updated; and the temporary Codex prompt has no net diff.

Do not claim B5 Files or later work is complete.
