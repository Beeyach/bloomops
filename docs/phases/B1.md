# B1 — Projects Core

## Objective

Build the first structured Release B work domain: Projects.

Projects are the parent operational container for later Milestones, Actions, Deliverables and Files. B1 must establish the data, authorization, lifecycle, activity and UI patterns those phases can safely build on without implementing them early.

Read:

- `docs/RELEASE_B.md`
- `docs/PRODUCT_SPEC.md`
- `docs/DOMAIN_MODEL.md`
- `docs/DESIGN_SYSTEM.md`
- `docs/DESIGN_CHECKLIST.md`

## B1 Owns

- Project relational schema and additive migration
- Project lifecycle and validation
- Project assignment relationship if needed for canonical responsibility/scope
- explicit workspace, Client and optional Service Engagement relationships
- Department metadata derived/validated without using Department as authorization
- Owner/Admin/Project Manager coordination access
- Team Member assignment-scoped Project access
- explicit Client visibility rules
- Project create/read/update lifecycle operations
- significant immutable Project activity
- internal Work/Projects surface
- Client detail Projects tab when meaningful
- minimal client-facing Project projection only for explicitly client-visible Projects
- responsive/accessibility verification
- security, tenant-isolation, concurrency and lifecycle tests

## B1 Does Not Own

- Milestones
- Actions/tasks
- dependencies
- Deliverables
- Files/assets
- comments
- approvals
- Social/Ads/Systems specialist workflows
- Finance
- notifications/queues
- Project templates or template UI
- automatic Project generation during activation/onboarding
- Release C/D/E/F features

Do not create placeholder runtime records for later phases just to make empty tabs render.

## Canonical Project Model

Use the durable domain vocabulary:

States:
- Planned
- Ready
- In Progress
- Waiting
- Blocked
- Review
- Completed
- Cancelled
- Archived

Useful fields include:
- workspace
- Client
- optional Service Engagement when service-specific
- Department metadata
- name
- owner/responsible membership
- health
- start date
- target date
- completed date
- client visibility
- client-facing label

Waiting means an expected dependency/person. Blocked means an unexpected impediment.

Status and health are separate facts. Do not invent automatic health scoring.

## Authorization

Follow the existing Identity → Role → Scope → Visibility model.

- Owner/Admin/Project Manager: workspace-wide delivery coordination.
- Team Member: no Project access merely from Department membership. Project access must come from an explicit supported assignment/scope relationship.
- Client: only their own explicitly client-visible Project projection. No internal notes, assignee identities that should remain private, hidden Service metadata, restricted activity, or other Clients.
- Project owner/assignee is responsibility, not authorization outside the existing policy model.
- Cross-workspace and cross-Client ID manipulation must be indistinguishable from missing resources where existence itself is sensitive.

## Lifecycle

Define explicit allowed Project transitions. Do not allow arbitrary request-body status writes.

At minimum test:
- ordinary forward transitions
- Completed timestamps
- Cancelled/Archived terminal behavior
- invalid transition refusal
- idempotent retries
- concurrent updates producing one stored transition and one semantic event

Do not mutate Client or Service lifecycle as a side effect of Project status.

## UI

Internal Work should gain a Projects destination/list that is useful without later phases.

Project detail in B1 should remain intentionally small: overview, Client/Service context, lifecycle/health/dates, responsibility and activity. Do not add empty Milestones/Actions/Files/Deliverables experiences merely to match future navigation.

Client detail may expose Projects when records exist. The Client portal may show explicitly client-visible Project summaries only if the read model can do so without exposing later-phase internals.

Use the established BloomOps design system. Avoid generic dashboard card grids and icon clutter.

## Security / Data Verification

Test at minimum:

- Project in Workspace A cannot be read or mutated from Workspace B
- Client A cannot fetch Client B Project by changing ids
- Team Member with no explicit Project/Client/Service scope cannot read it
- Department membership alone grants nothing
- assigned Team Member sees only supported assigned scope
- Client sees only client-visible Project fields
- Service Engagement, when supplied, must belong to the same Client/workspace
- responsible membership/owner must belong to the same workspace and be a valid internal member
- concurrency does not duplicate Project activity
- status/health remain separate
- no Client or Service lifecycle side effects

## Migration Safety

Use an additive migration. Do not rebuild or rewrite Release A tables. Preserve zero-to-current and no-op second-pass guarantees.

## Exit Criteria

B1 is complete only when:

- Project domain and migration are coherent
- authorization and isolation are proven
- lifecycle and activity are tested under retries/concurrency
- internal Project UI works on desktop/mobile
- relevant Client-safe projection is proven if included
- full existing Release A tests still pass
- local migration, Worker, browser and build checks pass
- `BUILD_STATE.md`, `DOMAIN_MODEL.md`, `INDEX.md` and Release B docs accurately describe the implemented result

Do not claim B2 work is complete.
