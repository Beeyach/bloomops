## Canonical Scheduling Rule

Calendar is a read projection over canonical Content facts. Do not create a second schedule state.

At minimum:

- `target_publish_date` remains the planning date owned by Content.
- C2 `stage` remains the production state.
- C2 `published_at` remains the server-owned publication timestamp.
- Calendar reads these facts and platform associations.
- Calendar rendering must never mutate Content.

If repository evidence proves one additional canonical scheduling field is necessary, document why. Prefer no duplicate scheduled date when `target_publish_date` already represents the intended publication date.

## Platform Associations

Use a relational association, expected conceptually as `content_platforms`, unless inspection proves a naming collision or stronger existing model.

Requirements:

- one Content Item can target multiple platforms/channels
- one platform value appears at most once per Content Item
- association belongs to the same workspace as the Content Item
- Content parent Client/Service remains fixed
- association changes do not mutate Content stage or dates
- no provider account IDs, tokens, post IDs or analytics in C3

### Platform vocabulary

Do not invent a broad provider taxonomy from model knowledge. First inspect `PRODUCT_SPEC`, `DOMAIN_MODEL`, existing UI/tests and repository history for canonical names.

If the repository still has no exact fixed platform allowlist, implement the smallest durable model that preserves future compatibility and is still safe, for example a normalized bounded platform key plus display label strategy documented in `DOMAIN_MODEL.md`. Do not silently hard-code arbitrary networks merely because they are common.

Whichever model is chosen, validation must be exact, normalized, bounded, non-empty and safe from control/bidi/malformed-Unicode abuse. Do not accept caller workspace/content identity inside a platform mutation body.

## Authorization

Preserve C1/C2 `Identity -> Role -> Scope -> Visibility` exactly.

- Owner/Admin coordinate reachable Content.
- PM ordinary Content follows C1/C2 scope; restricted still requires exact current Client/Service assignment.
- Team may edit platform associations only inside the same current Client/Service scope that permits Content fulfillment.
- Content owner, Department membership, Project assignment and Action-only assignment remain non-grants.
- Client has no C3 internal Calendar/Content access.

Platform associations never widen Content reach. Every list/calendar/platform mutation must start from current Content readability.

## Platform Writes And Concurrency

Use revision/CAS or an equally strong current-domain mechanism so platform changes cannot race silently with one another or with Content visibility/scope changes.

Prove:

- duplicate add converges or safely conflicts without duplicate rows
- remove of a missing association is a safe no-op or explicit conflict, consistently documented
- simultaneous add/remove/edit operations leave one canonical association set
- scope/visibility revocation between render and commit fences the write
- semantic activity and association facts commit atomically
- response-loss retry does not duplicate semantic history

Do not create a generic new idempotency framework if existing request/revision patterns are sufficient.

## Activity

Record significant platform association changes in immutable `activity_events` using small facts only.

Prefer a compact canonical event strategy such as one platform-set-changed event, or add/remove events if current repository conventions make that clearer. Do not store the mutable platform set only in activity metadata.

Internal Client history must continue to filter Content-related events by current Content readability. Clients still receive no internal Content history in C3.

## Calendar Projection

Provide a useful internal Social calendar without a duplicate calendar table.

Minimum behavior:

- show Content whose canonical target publish date falls inside the requested calendar range
- include current stage and platform labels
- distinguish Published using current stage/published timestamp, not a copied flag
- useful Client/platform filters
- deterministic ordering for multiple items on the same date
- hidden records must not affect counts, overflow or empty states
- current assignment/restriction changes remove rows immediately
- calendar reads write nothing

Choose a bounded range contract appropriate for D1 and document it. Month view is the default useful target if consistent with the existing UI. A week/list fallback is acceptable if repository evidence makes month layout unsafe, but do not build an unbounded timeline.

### Date semantics

Use exact real calendar dates. Reuse existing Client/workspace date helpers where relevant; do not invent timezone semantics that conflict with B3/C1. `target_publish_date` is a date, not an instant. `published_at` is an instant.

Calendar range query parameters must be exact, validated and bounded. Unsupported/duplicate query values return sanitized 400 after authorization where required by B7/C1 rules.

## Implemented contract and local evidence

C3 implementation uses `0015_c3_calendar_platforms.sql`: a four-column relational association with composite workspace/Content/key primary key, direct workspace FK, composite Content FK, bounded key/label CHECKs and a platform filter index. Content remains 24 columns and now has seven indexes. The journal has 16 migrations and the schema 38 tables. Historical C1/C2 migrations, triggers, package/lockfile, Worker configuration and File subjects are unchanged.

Repository docs/history provide no fixed network allowlist. The durable model therefore accepts 0–12 channel labels, NFC-normalized/trimmed/space-collapsed, bounded to 60 UTF-16 units; lowercase NFC keys allow 120 units for case expansion. Controls, format/bidi characters, malformed Unicode and duplicate normalized keys reject the whole set. Code-point ordering matches SQLite BINARY order. `DOMAIN_MODEL.md` records exact semantics, including significant display-spelling edits and silent current-revision identical-set/missing-removal no-ops.

Creation writes initial associations with Content and creation provenance atomically. Dedicated PUT platforms/expectedRevision replaces one canonical set using Content CAS. A single immutable set-change event, conditional deletion/insertion and the revision update commit atomically, with revision updated last. Every statement rechecks live authorization. Identical consumed-revision retries acknowledge the original event under current Content access without restoring old state; competing different sets, removal, detail or stage edits have one winner. Parent and stage/date facts never change through platform edits.

Calendar GET requires exact inclusive 1–42-day ranges and allowlisted Content filters. It selects current-readable target dates, current C2 stage/publication and platform associations in one bounded SQL query, ordered date/ID ascending, with 200 visible rows plus one visible overflow probe. No row duplication, assigned-ID bind expansion, per-item API/DB calls, writes or R2 access is introduced. Dates use the existing 0100–9999 helper range; target dates remain floating dates while publication remains an instant.

The UI is a monthly agenda grouped by date with UTC-current-month default, Client/platform/stage filters, month/page navigation, complete dense same-day rows and an undated-item explanation. Inspection found the inherited seven-column `DatabaseViewNode` calendar draggable and title-only; agenda rows preserve long titles and multiple labels at all required widths. Explicit date editing stays in Content details. List/create/edit/detail expose platform filtering/editing using existing Bloom primitives.
