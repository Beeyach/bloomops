## Core Rule: Conditional Pipeline, Not Free-Form Status

Callers may never set `stage` directly through the ordinary Content edit route. C2 adds a dedicated transition operation that validates the current stage, target stage, workflow flags, required context, current revision and current authorization.

The transition engine derives legal next steps from canonical Content facts. It must not store a second pipeline status, duplicate completion booleans or shadow stage table.

## Pipeline Semantics

The default forward path is:

Idea -> Script -> Waiting for Recording -> Editing -> Internal Review -> Client Review -> Approved -> Scheduled -> Published

Conditional skipping uses C1 flags:

- if `recording_required = false`, Waiting for Recording is skipped
- if `internal_review_required = false`, Internal Review is skipped
- if `client_approval_required = false`, Client Review is skipped

The transition engine should expose the next applicable forward stage, not require callers to know how to skip disabled stages.

### Revision Requested

Revision Requested is a controlled branch from review, not an arbitrary destination.

- It may be entered from Internal Review or Client Review.
- Entering Revision Requested requires a bounded non-empty revision reason/context.
- Revision Requested returns to Editing for the next production pass.
- It does not create an approval round in C2. C5 owns formal approval history.

### Waiting for Recording

Waiting for Recording is valid only when `recording_required = true`.

If C2 stores waiting context, keep it on Content as small canonical workflow context owned by this phase, not in activity metadata as mutable state. Do not add actual recording upload behavior. C4 owns recordings/assets.

### Approved

Approved is the internal Content stage only. In C2 it is a coordinator-managed production state, not proof of a formal Client approval round. C5 will add append-only approval records and may refine approval behavior.

### Scheduled

Scheduled means production is ready and intended for publication. C2 does not add platform/channel associations or a calendar. C3 owns those.

### Published

Published is terminal for C2.

- only the transition engine may set `published_at`
- `published_at` is server-generated exactly once on the winning transition
- no ordinary edit may set, clear or rewrite it
- repeated response-loss retry of the same already-published fact should converge safely rather than create a second semantic event

Do not add unpublish/reopen behavior in C2 unless current canonical docs already require it. Prefer Published terminal.

## Backward/Rework Behavior

Do not add a generic back button between all stages.

The explicit rework path is Review -> Revision Requested -> Editing. Other backward movement remains unavailable unless repository evidence proves a required operational case.

## Workflow Flag Changes

C1 allows editing workflow flags. C2 must define their effect safely:

- changing a flag does not silently mutate the current stage
- transition eligibility uses the current flags at transition time
- disabling a stage while an item is already in that stage must not corrupt history or auto-jump the item
- existing current stage remains valid; next forward resolution skips newly disabled future stages

## Authorization

Preserve C1 `Identity -> Role -> Scope -> Visibility` exactly.

- Owner/Admin coordinate reachable Content.
- Project Manager coordinates ordinary reachable Content; restricted Content still requires the exact current Client/Service assignment required by C1.
- Team Member may transition Content only inside the same current Client/Service assignment scope that allows C1 fulfillment.
- Content owner, Department membership, Project assignment and Action-only assignment remain non-grants.
- Client has no C2 internal transition access.

Do not weaken C1 scope because a stage button would otherwise be inconvenient.

## Transition Authorization at Commit Time

Every transition must re-check current database truth inside the committing condition:

- active workspace
- active membership with unchanged user/role identity
- current Client/Service parent validity
- current canonical Social Service relation when service-bound
- current assignment scope for PM/Team where required
- current Content visibility
- current revision
- current source stage

Revocation/reassignment/restriction between page render and transition commit must fence the write.

## Concurrency and Retry

Transitions use strict revision CAS.

Prove:

- competing different transitions from one revision have one winner
- transition versus ordinary edit has one winner
- two identical concurrent transitions do not append duplicate semantic history
- stale losers return sanitized conflict
- revision increments exactly once per committed transition
- stage event and fact commit atomically
- injected late failure rolls back both
- response-loss retry after a committed transition converges safely without a duplicate event
- Published timestamp is from the winning commit only

If a request id is useful for response-loss convergence, use a bounded UUID mechanism consistent with current domain patterns. Do not create a broad new generic idempotency framework in C2.

## Activity

Add one canonical significant transition event, preferably `CONTENT_STAGE_CHANGED` unless current activity conventions strongly justify more specific event codes.

Activity should record small immutable facts such as from stage, to stage, and bounded reason/context when applicable. Do not store the whole Content body or make activity metadata the source of current stage/revision context.

Internal Client history may describe Content stage changes only when the current Content item is still readable to that actor. Clients still receive no internal Content history in C2.

## C2 Acceptance Story

Prove at least one real local story:

1. Create Content variants with each combination of workflow flags.
2. Show the default forward path and each conditional skip.
3. Recording-required Content enters Waiting for Recording; recording-disabled Content cannot enter it.
4. Internal-review-disabled Content skips Internal Review.
5. Client-approval-disabled Content skips Client Review.
6. Internal Review and Client Review can request revision with required bounded reason; Revision Requested returns to Editing.
7. Published gets one server timestamp and is terminal.
8. Team fulfillment transitions only within current Client/Service assignment scope.
9. Restricted PM/Team access still requires the exact C1 assignment.
10. Owner/Department/Project/Action-only responsibility does not grant transition access.
11. Competing transition/edit and transition/transition races produce one fact/revision/event winner.
12. Revoking scope or changing visibility while a session remains issued immediately fences transition.
13. Clients cannot access internal C2 routes or stage mutation.
14. No transition mutates Client, Service, Project, Action, Deliverable, File or Onboarding lifecycle.
