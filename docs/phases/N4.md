## Required user workflow

An authorized template author defines and saves a reusable job setup. A delivery
manager chooses that saved version, an authorized Client and optional purchased
Service, enters a new event name and date, reviews the exact generated Project,
Milestones, Actions, Deliverables, dates and dependencies, then explicitly creates
the new job once. Open the real generated Work records afterwards. Reuse the setup
for another event without changing the earlier job. Retries must return the first
generation; changed intent must conflict. No preview is permission to write.

Reuse canonical templates/template_versions and Work Core records. Preserve the
existing Systems blueprint and onboarding engines; no second task lifecycle.
Definitions and generation provenance are immutable snapshots. Template revisions
must not mutate generated work. Explicitly retiring a setup prevents new use while
preserving previous jobs and provenance.

## Bounded implementation decisions

- Author fresh structured setups under template kind `project`. Do not implicitly
  harvest a Client's private project, notes, files, credentials or operational state.
  The setup contains named Milestones, Action/Deliverable titles and optional plain
  instructions, relative dates and Action dependencies. The author reviews exactly
  what the reusable definition contains before saving its version.
- Stable logical keys identify rows and references. Bound definitions to20
  Milestones,60 Actions,20 Deliverables and180 dependency edges; reject cycles,
  duplicate or dangling keys, unsupported fields and oversized definitions.
- Dates are Client-local calendar dates, as in Work Core. Signed integer offsets
  from the chosen event date express calendar days, including weekends. Null means
  undated; zero means the event date. No timezone-dependent instant conversion or
  unapproved holiday/business-day rule. Offsets are bounded to ±3660 days. Validate
  the final ISO dates and start/target ordering; reject out-of-range years.
- A literal `{{event}}` token in labels/instructions substitutes the new event name.
  No expressions, scripts or arbitrary template execution. Bound expanded content
  using the actual Work Core limits.
- New records always start internal: Project planned/on-track, Milestones upcoming,
  Actions to-do/normal priority, Deliverables planned. No owners/assignees, approvals,
  client visibility, credentials, audiences, files, connections, send/schedule state
  or prior completion is copied. Assignment and visibility use normal later Work
  operations. The preview explains these defaults.
- Template authoring/retirement requires current internal `templates.manage`
  capability (including explicit grants), using existing capability rules. Listing
  and preview are limited to current internal delivery managers or template authors.
  Generation independently requires existing `project.create` authority for the
  selected Client and a valid open same-Client Service if supplied. Client/portal
  and preview identities cannot enter this workflow. Every read/retry/write rechecks
  current workspace membership, capability and resource access.
- Versioned definition saving and generation need durable, actor/workspace-scoped
  request identities. Reuse the repository's guarded D1 batch pattern, canonical
  definition encoding and relational generation-provenance conventions. A failed,
  denied, conflicting or zero-row claim creates no partial job or activity. Any
  additive storage will be generated through the normal migration workflow.

## Pages record context — next integrated batch

NEXT_PHASES.md requires Pages linked to canonical Clients and Projects; DOMAIN_MODEL
describes optional Client/Project Page metadata. Existing P4 and N1F already supply
the editor, nested links, sharing, search and recovery. Preserve those workflows.

Implementation decisions for this batch:

- A Page may name one Client and, optionally, one Project belonging to that Client.
  This is organizational context, not a new authorization grant, copied record,
  inherited association or operational status. Child Pages remain independently
  associated; moving a Page does not change its context or document content.
- Current Owner/Admin Page administrators explicitly choose, change or remove the
  context through the Page UI. Use canonical Client/Project access and same-workspace
  relationships. Other Page editors may continue writing without managing context.
- Display context only when the viewer can currently read both the Page and the
  relevant record. A shared Page never grants Client/Project access, and a linked
  Client/Project never grants Page access. Portal users see only their authorized
  account and client-visible Project destinations; no internal navigation. Use the
  existing Portal Home Project summary with a stable Project anchor and its canonical
  client-facing label; there is no separate portal Project-detail page.
- Internal Client/Project destinations list only currently readable linked Pages,
  filtering before pagination. Use bounded searchable choices and deterministic
  pagination; no body snippets, inaccessible counts or per-row permission requests.
- Save context separately from document body revisions. Bind requests to the actual
  user/workspace, compare the expected context revision in SQL, retain failed input,
  confirm an unchanged save without duplicate effects, and give a clear conflict
  recovery action. A failure or zero-row write must not report success. Do not
  serialize user-provided URLs or trust hidden UI controls.
- Additive relational constraints must bind Page, Client and Project workspace
  values and the actual Project/Client relationship. Preserve existing Page rows,
  content, hierarchy, grants and deletion restrictions. No migration of old content
  into inferred associations.

Finish line: choose context in the real Page editor, save/reopen it, open the current
authorized Client/Project, return to the same linked Page from that record, change
or remove context without changing writing, and retain safe links across Page moves
and sharing/revocation. Verify real disposable storage, concurrent changes, empty
and populated lists, hidden candidates, foreign IDs, portal and revoked permissions,
delayed UI responses, keyboard/narrow layout and completed-Worker interaction.
Page templates remain the following agreed Pages workflow; this batch does not
declare the entire N4 or recovery inventory finished.

## Reusable Page templates — implementation decisions, 16 September 2026

NEXT_PHASES requires Page templates alongside the existing editor, links and
recovery. This batch makes that requirement usable without replacing the editor.

- A current Owner/Admin (`pages.manage`, also the existing role-level
  `templates.manage`) captures the **saved** title/body of an existing Page as an
  immutable reusable version. The panel identifies the saved Page revision and
  requires an explicit save-template action. Unsaved editor content is not captured.
- The source Page remains the normal editable document. After editing and saving it,
  the author can capture another version. Earlier versions and Pages already created
  from them never follow those edits. Retirement hides a template from new creation;
  restoration is explicit. The catalogue/preview and mutations remain internal to
  current Page administrators. No portal template catalogue or capability expansion.
- Creating from a reviewed, current active template version makes one new private
  top-level Page through the canonical Page creation transaction. It copies title
  and document body only: no child Pages, record associations, grants, comments,
  approvals, operational records or external sending. Existing references in the
  document remain references and retain their independent authorization. The normal
  editor, hierarchy, sharing and recovery are used on the created Page.
- Creation UUIDs are scoped to the authenticated workspace/user and fixed version.
  Retries confirm the same created Page without overwriting later writing; different
  UUIDs create distinct Pages. Changed intent conflicts. Snapshot capture and new
  Page creation use D1 batches, SQL current-authority/version guards and atomic
  completeness checks, including a zero-row insert. Lost responses retain a retry
  action. A stale catalogue requires reopening the current version.
- Canonical operational `templates.kind` currently permits onboarding/project/
  social/systems/ads, not documents. Small Page-specific immutable snapshot and
  creation-provenance tables preserve that contract and the existing Page writer;
  no operational-template reclassification or second document editor is introduced.
- Validate snapshot size/title using existing Page limits. Render stored document
  bodies with existing safe Page rendering. Preview and create both recheck current
  authority; a shared source Page never grants template administration.

Finish line: real Page editing → explicit saved-version capture → catalogue and
saved preview → new private editable Page → retry without duplication → source edit
and new version with the first Page unchanged → retire/restore. Cover current and
revoked authority, foreign workspaces, portal rejection, concurrent writes, failed/
zero-row batches, immutable snapshots, and keyboard/narrow/error states. Disposable
native D1, populated upgrade, full suite, completed build and actual Worker browser
checks are required at integration. Exact focused commands will be recorded with
those harnesses. This does not declare all N4/Operations or recovery complete.
