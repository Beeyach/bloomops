## Core Rule: Projection, Not State

B6 must project existing canonical records. It must not maintain a second status, health, progress, overdue, waiting, review, delivery or file-state fact.

Prefer relational queries or reusable read-model functions over a new schema migration. A B6 schema migration is not expected. Add one only if repository evidence proves a small additive relational structure is genuinely required and cannot be represented safely as a query over canonical records. If no migration is needed, explicitly document that B6 is schema-free.

The durable canonical sources remain:

- Project status/health on Project
- Milestone status on Milestone
- Action status/priority/due date/waiting/dependency edges on Action/dependencies
- Deliverable status/visibility on Deliverable
- File metadata/state/visibility/link on B5 File records
- Client/Service/Onboarding facts on their own records

## Internal Home Goals

Release A Home is currently orientation. B6 replaces that later-release placeholder with a useful operational dashboard.

Home should help an authorized internal user answer, without opening every Project:

- What needs my attention today?
- What is overdue?
- What is waiting?
- What is in review?
- Which Projects need attention?
- What client-facing output is coming up or in review?
- What was recently delivered or uploaded, where current visibility allows it?

Do not turn Home into a generic SaaS metric wall. Prefer a calm editorial hierarchy with a few high-value sections and compact rows.

Useful candidate sections, subject to actual repository evidence and role scope:

- My work / Today
- Overdue Actions
- Waiting Actions
- Review Actions
- Projects needing attention
- Upcoming Deliverables or Client Review Deliverables
- Recently delivered outputs
- Recent Ready Files where meaningful

Not every actor needs every section. Empty sections should normally disappear rather than show decorative zero cards.

## Work Area

B3 already implements Mine, Today, Upcoming, Waiting, Review, Overdue and All for Actions with Client, Department, Service, Project, Assignee, Status and Priority filters.

B6 should preserve those canonical Action views. Improve them only where composition, summaries, navigation, empty states or B4/B5 context makes the Work experience materially more useful.

Do not replace B3 Action queries with dashboard-specific duplicate logic if the same canonical helper can be reused.

The Projects tab should remain separate from Actions. B6 may enrich Project rows with bounded canonical summary information, such as:

- Project status/health
- next target date
- Milestone finished progress when readable
- open Action count or concise Action state summary
- Deliverable status summary
- File presence where meaningful

Any summary must be computed from currently readable rows. Hidden/restricted children must not affect a Team Member's or Client's visible counts, percentages, labels or empty-state decisions.

## Role and Scope Behavior

Preserve `Identity -> Role -> Scope -> Visibility`.

### Owner/Admin/Project Manager

May receive workspace-wide coordination projections to the extent their existing canonical permissions allow. Restricted children still follow their current explicit assignment rules.

### Team Member

Home and Work must remain assignment-scoped. Action-only assignment may surface that Action with only the minimal parent context already allowed by B3. It must not cause unrelated Project, Deliverable, File, Client or sibling summary counts to appear.

Project/Client/Service assignments may project the records already reachable through those scopes. Department membership and Project ownership remain non-grants.

### Client

B6 is primarily internal Home + Work composition. Do not invent Client access to internal Actions or activity. Existing Client portal Home/Project/Milestone/Deliverable/File projections may be composed more cleanly only if needed, while preserving exact B1-B5 allowlists and no-hidden-count guarantees.

## Date and Time Semantics

Reuse B3 deterministic Client-local calendar-day behavior for Action Today/Upcoming/Overdue. Do not invent a global dashboard timezone fact.

Where Home summarizes dated Deliverables or Projects, use the canonical stored date and clearly defined comparison semantics. Tests must freeze or inject time and cover opposite sides of midnight and at least one daylight-saving boundary where the current Action behavior does.

Dependency-blocked Actions remain excluded from ordinary Overdue exactly as in B3.

## Project Attention Projection

Do not create a new stored Project attention state.

A Project may qualify for an attention section from existing canonical facts, for example:

- health is Needs Attention or At Risk
- status is Waiting or Blocked
- readable overdue Actions exist
- readable Actions are in Review/Waiting where useful
- client-visible Deliverables are in Client Review where useful for coordinators

If B6 introduces an aggregated attention reason, it must be a deterministic read model with clear priority/ordering and tests. It must not silently rewrite Project health or status.

## Deliverable and File Composition

Deliverables remain separate from Actions. Files remain metadata in D1 with bytes in R2.

Home/Work may surface Deliverable/File summaries only from current readable records. Never expose:

- storage keys
- hashes
- upload lease/generation details
- hidden counts
- internal Deliverable titles to Clients when the B4 safe label rules would hide them
- uploader identities where the current B5 projection excludes them
- archived or failed Files as Ready/current output unless the existing File model explicitly allows it

Do not perform R2 object reads merely to render dashboard summaries. Dashboard composition should normally use canonical D1 metadata.

## Recent Activity

If recent delivery/upload information is useful on Home, prefer canonical `activity_events` filtered through the current record visibility rules already established in B1-B5.

Historical titles must disappear immediately when current scope or visibility no longer allows the underlying record.

Do not expose raw internal activity to Clients in B6.

## Performance and Bounds

All dashboard sections must be bounded and deterministic.

- Avoid loading entire workspaces into memory.
- Use relational predicates, indexes and limited queries.
- Reuse B1-B5 relational authorization conditions to stay below D1 bind limits.
- Do not build huge `IN (...)` lists from assigned IDs.
- Prefer section limits appropriate for a dashboard, with links to full Work/Project surfaces for more.
- If counts are shown, compute them from canonical readable rows and do not leak hidden totals.

The dashboard should remain useful for approximately ten active agency Clients without becoming visually or query heavy.

## Internal Home UX

Keep the BloomOps design direction: calm, premium, editorial, minimal clutter.

Prefer:

- one clear page heading
- a concise first section for urgent personal work
- compact operational sections below
- strong text hierarchy
- plain-language status labels
- direct links to existing Action/Project pages

Avoid:

- generic KPI-card grids
- icon clutter
- fake productivity scores
- charts that add no operational value
- hardcoded sample metrics
- empty future modules

Home must remain useful at 1440, 1024, 768, 390 and 320 widths.

## API and Security

B6 may be implemented entirely through server components/read models. Add new API routes only if there is a real interaction that cannot use the existing route surface.

Any new protected route must preserve A11/B1-B5 rules:

- real session identity
- live membership/workspace/scope checks
- exact visibility predicates
- strict query/body allowlists
- safe 400/403/404/409/500 behavior
- no raw SQL, stack or constraint text
- `no-store`
- guessed/foreign IDs fail without existence leaks

No dashboard query may bypass child visibility merely because the parent Project is readable.

Prove at least one end-to-end B6 story over the real local Worker/database:

1. Seed a multi-service Client with multiple Projects, Milestones, Actions, dependencies, Deliverables and Files using canonical B1-B5 operations/fixtures.
2. Owner/Admin/PM Home shows a bounded useful operational summary from currently readable facts.
3. Mine/Today/Upcoming/Waiting/Review/Overdue/All remain correct, including Client-local date logic and dependency-blocked overdue exclusion.
4. Project summaries accurately reflect readable Milestone/Action/Deliverable/File state without changing any parent or child lifecycle.

8. Empty dashboards remain calm and useful rather than rendering fake zero metrics.
9. Every summary links to the existing canonical record surface rather than creating a second management path.
