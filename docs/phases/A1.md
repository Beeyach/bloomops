# A1 — Infrastructure Isolation

## Objective

Give BloomOps its own deployment and storage boundaries without changing product behavior.

## Required Work

Create isolated BloomOps environments:

- development
- staging
- production

Use separate:

- Cloudflare deployment resources
- D1 databases
- R2 buckets
- secrets/config

Do not reuse the Leadsthatbloom production database.

## Deployment Foundation

The inherited app currently uses the old Leadsthatbloom deployment architecture.

Migrate BloomOps to the current supported Cloudflare deployment path appropriate for Next.js/Workers at implementation time.

Research current official Cloudflare guidance before choosing exact packages/configuration.

Do not mix infrastructure migration with product redesign.

First prove that the inherited application runs under the new BloomOps deployment foundation.

## Environment Rules

Never point preview/staging at production client data.

Inherited environment names such as `LTB_*` should not become permanent BloomOps configuration.

New BloomOps-specific names should be used for BloomOps secrets/config.

## R2

Set up isolated R2 bindings early.

No full uploader is required in A1.

Only prove environment-correct binding/access.

## Verification

Required:

- local build passes
- existing tests pass or inherited failures are documented
- staging deployment succeeds
- BloomOps D1 binding resolves
- BloomOps R2 binding resolves
- staging cannot access production data
- no Leadsthatbloom resources are changed

## Scope Boundary

Do not:

- add Better Auth
- add Drizzle domain schema
- redesign navigation
- remove prospecting code
- build Clients
- build Onboarding

Stop after infrastructure isolation is verified.
