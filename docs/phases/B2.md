## Canonical Milestone Model

A Milestone belongs to exactly one workspace and one Project. Client, Service Engagement, and Department context are derived from that Project rather than duplicated as independent Milestone facts.

Canonical states:

- Upcoming
- In Progress
- Waiting
- Completed
- Skipped

Useful fields:

- workspace
- Project
- internal name
- optional client-facing label
- status
- position/order
- optional start date
- optional target date
- completed timestamp owned by the server
- visibility
- revision/concurrency token if needed by the implementation
- created/updated timestamps

The internal name is required and bounded. The client-facing label is optional and must never be used to infer visibility. Dates must be valid calendar dates and target must not precede start when both exist.

Status is a Milestone fact only. Creating, editing, reordering, completing, or skipping a Milestone must not mutate Project status/health, Client lifecycle/health, Service lifecycle, Onboarding, or Department membership.

## Lifecycle

Use an explicit transition matrix rather than arbitrary request-body status writes. The smallest coherent B2 matrix is:

| From | Allowed next states |
|---|---|
| Upcoming | In Progress, Waiting, Skipped |
| In Progress | Waiting, Completed, Skipped |
| Waiting | In Progress, Completed, Skipped |
| Completed | None |
| Skipped | None |

Every Milestone starts Upcoming. Entering Completed records one server-owned completion timestamp. Completed and Skipped are terminal in B2. Identical retries must be no-ops. Competing stale changes must conflict rather than silently overwrite each other.

Do not invent automatic Project completion when all Milestones finish. Release B dashboards may project Milestone state, but the Project remains the sole owner of Project lifecycle.

## Ordering

Milestones have one deterministic order per Project.

The implementation may use integer positions and a bounded reorder operation, but ordering must satisfy all of these:

- Project A ordering can never change Project B
- guessed or foreign Milestone IDs cannot enter another Project's order
- one reorder mutation commits atomically with its semantic activity
- duplicate or missing IDs are rejected when an operation expects a complete ordered set
- concurrent/stale reorders cannot produce silent lost updates
- ties, if the storage design permits them transiently, still read deterministically
- retries of the winning order are no-ops and do not duplicate activity

Prefer the smallest relational design that preserves those guarantees. Do not add a second Project-status fact just to coordinate ordering.

## Authorization and Visibility

Follow the existing Identity -> Role -> Scope -> Visibility model and B1 Project scope.

- Owner/Admin/Project Manager may coordinate Milestones for Projects they can manage.
- Team Member remains read-only in B2. A Team Member sees a Milestone only when the parent Project is in scope through the existing Client, Service, or explicit Project assignment rules.
- Department membership alone grants nothing.
- Milestone ownership/assignment is not introduced in B2.
- Client sees only Milestones for their own currently linked Client, only when the parent Project is explicitly client-visible, and only when the Milestone itself is explicitly client-visible.
- An internal or restricted parent Project always caps child visibility.
- A restricted Milestone is internal-only and follows the existing restricted-record rule. Owner/Admin may see it; Project Manager/Team Member require the explicit Project assignment already used by B1 restricted Project access. Client never sees restricted work.
- Cross-workspace, cross-Client, cross-Project, and guessed-ID access must fail without leaking existence.

Use dedicated Client-safe projections. Never serialize raw Milestone rows to the portal.

## Progress Projection

Progress is derived, never stored as a second status fact.

Internal Project progress may summarize all Milestones the actor may currently read. Client progress must use only Milestones visible to that Client under the parent Project visibility rules.

For progress math, Completed and Skipped are terminal/finished states. Use language such as `finished` rather than claiming a skipped Milestone was completed. If there are zero visible Milestones, do not fabricate a percentage or render an empty progress module.

Hidden/restricted Milestones must not affect Client counts, percentages, labels, or empty-state decisions.

## Activity

Record significant Milestone changes in canonical `activity_events` with `subject_type='milestone'`, the Milestone subject ID, and Client/Service context derived from the parent Project.

At minimum distinguish:

- created
- details changed
- status changed
- order changed

Events must commit atomically with the fact they describe. Retries and concurrent losers must not duplicate semantic history. Any Project-level history projection that includes child Milestone events must filter by the Milestone's current readable visibility so old events cannot leak after a visibility restriction.

Clients do not receive internal Milestone activity in B2.

## UI

Integrate Milestones into the existing internal Project detail rather than building a separate generic module just to fill navigation.

The Project detail should support, when authorized:

- ordered Milestone list
- create Milestone
- edit name/client label/dates/visibility
- explicit status controls
- reorder controls that work with keyboard and touch
- clear finished/waiting state
- progress summary only when Milestones exist

Team Members get a read-only version according to scope.

The Client portal may show an ordered Milestone summary only under an explicitly client-visible Project and only for client-visible Milestones. Keep the projection calm and plain-language. Do not expose internal names when a safe client label is intended, internal IDs beyond the existing opaque route/resource ID, Service/Department IDs, revisions, hidden counts, assignees, or internal activity.

Use the existing BloomOps design system. Avoid generic dashboard card grids, icon clutter, and empty future-feature tabs.

## Security and Concurrency Verification

Test at minimum:

- Workspace A cannot read or mutate Workspace B Milestones
- Client A cannot fetch Client B Milestone by changing Project or Milestone IDs
- Milestone cannot be attached to a foreign Project or workspace
- Team Member with no Project/Client/Service scope sees nothing
- Department membership alone grants nothing
- explicit Project assignment grants the Project and its readable Milestones, not the parent Client or sibling Projects/Services
- parent Project visibility caps child visibility
- Client projection is an exact allowlist and excludes hidden/restricted Milestones from both rows and progress math
- visibility/contact/membership revocation takes effect against stale actors/sessions
- lifecycle refuses arbitrary/invalid transitions
- identical status retries create one stored transition and one event
- competing status edits conflict cleanly
- reorder rejects foreign/duplicate/missing IDs and is atomic under concurrency
- late activity failure rolls back the Milestone mutation/order change
- malformed/non-object JSON returns safe 400 responses
- unexpected failures are sanitized and protected responses retain `no-store`
- no Client, Service, Onboarding, or Project lifecycle side effects

## Acceptance Story

Prove at least one end-to-end B2 story over the real local Worker/database:

1. An authorized coordinator opens an existing B1 Project and creates several ordered Milestones.
2. Milestones can be edited, reordered, moved through valid lifecycle states, and retried without duplicate facts/history.
3. Progress updates from canonical Milestone state while Project status remains unchanged.
4. A scoped Team Member can read only the Project/Milestones allowed by existing B1 scope and cannot coordinate them.
5. A Client sees only the client-visible Project and client-visible Milestones, in order, with progress computed only from what that Client can see.
6. Hiding/restricting a Milestone or revoking the contact/scope removes it immediately without leaking prior activity or hidden counts.
