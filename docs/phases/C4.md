## Core Storage Rule

C4 must extend the B5 File model, not create parallel upload metadata and not store bytes in D1.

Canonical ownership remains:

- D1 owns File metadata, authorization facts, fixed attachment identity and recovery attempts.
- R2 owns bytes.
- R2 keys remain server-generated and opaque.
- authenticated download resolves the File row and current attachment authorization before using the canonical R2 key.

Reuse the existing `assets` and `asset_upload_attempts` lifecycle wherever possible.

B5 `asset_links` is deliberately fixed to Project/optional Deliverable and carries strong composite foreign keys. Prefer a new additive Content-specific fixed link table, conceptually `content_asset_links`, rather than weakening or rebuilding B5's existing link shape merely to make it generic.

A safe C4 link should cover only what Content needs, conceptually:

- asset id
- workspace id
- content id
- attachment purpose
- created timestamp

Use repository naming conventions after exact inspection.

The Content link must have same-workspace relational foreign keys to both the File and Content Item. The link is fixed after creation. No mutable relinking to another Content Item.

One File must not silently belong to both the B5 Project/Deliverable attachment family and the C4 Content attachment family. Enforce attachment-family exclusivity with relational design and/or database triggers if the existing schema cannot express it with one foreign key.

Do not create a generic polymorphic subject table for future Request/Page/Finance/Ads domains.

## Attachment Purpose

C4 needs a small exact Content-specific purpose vocabulary.

At minimum distinguish:

- `recording` - source media supplied for Content production
- `asset` - another Content-specific working/delivery asset

Do not invent a large asset taxonomy. Purpose is not authorization and does not change Content stage.

A Client may upload only `recording` purpose in C4. General Content assets remain internal upload behavior.

## Relationship to C2 Pipeline

Recording upload must not auto-transition the Content pipeline.

In particular:

- uploading a recording does not automatically move Waiting for Recording to Editing
- archiving a recording does not move a stage backward
- asset visibility changes do not mutate Content workflow flags or stage
- File operations never change Content target date, platforms, publication timestamp, Client, Service, Project, Action, Deliverable or Onboarding state

The coordinator or assigned fulfillment user uses the existing C2 transition operation after reviewing the recording.

## Internal Authorization

Preserve C1-C3 `Identity -> Role -> Scope -> Visibility` and intersect it with File visibility.

- Owner/Admin may coordinate Content Files across current workspace Content scope.
- Project Manager follows C1-C3 Content rules. Restricted Content still requires the exact current Client or Service assignment.
- Team Member may work with Content Files only where the same current Client/Service assignment already permits Content fulfillment.
- Content owner, Department membership, Project assignment and Action-only assignment remain non-grants.
- A Content File never widens access to its Content parent.

Because Social Team members can edit and transition Content inside assigned scope, C4 may give them the Content-specific upload/retry/archive actions needed for fulfillment if the implementation proves those actions remain capped by current Content scope. Do not loosen the existing B5 Project File policy merely to accomplish this. Use Content-specific authorization where needed.

Internal File visibility remains `internal`, `client` or `restricted`. Effective access is the intersection of:

1. current actor/session/workspace truth
2. current Content parent readability
3. current File status
4. current File visibility
5. current attachment purpose/action policy

## Client Recording Authorization

C4 introduces only the minimum Client write path required to receive recordings.

A Client recording upload must require all of the following current database facts:

- authenticated Client membership in the same active workspace
- current `client_contacts.user_id` linkage to the exact Content Client
- Content visibility = `client`
- Content still belongs to that exact workspace/Client and, if service-bound, the canonical same-Client Social Service
- `recording_required = true`
- current stage = `waiting_for_recording`
- attachment purpose = `recording`

The Client must not be able to upload a general asset, select another Client/Service/workspace, choose an object key, choose uploader identity, or choose Internal/Restricted visibility.

Client-uploaded recordings should use a fixed client-safe visibility policy selected by the server. Prefer `client` visibility unless exact existing File semantics prove another choice safer.

Revoking the Client contact link, changing Content visibility, leaving Waiting for Recording, suspending/removing the membership/workspace, or changing canonical parent truth must immediately fence new uploads/retries and subsequent downloads.

Do not give a Client generic Content edit, platform, pipeline or internal activity access in C4.

## Minimal Client Surface

C6 owns the general Client Content portal. C4 may add only the narrow UI necessary to fulfill a current recording request.

Preferred shape:

- a conditional Recording Needed/Recording Request module or dedicated recording route inside the existing Client portal shell
- visible only when at least one currently eligible Content Item satisfies the Client recording rules above
- upload/retry/download state for the exact recording File
- no general Social/Content navigation if it would expose unfinished C6 concepts

Use a dedicated allowlisted client DTO. Do not leak:

- internal owner identity
- script, hook, caption or CTA
- revision number
- service/department/internal ids beyond the opaque Content/File ids needed by the route
- internal activity
- hidden file counts
- R2 key/hash/lease/attempt metadata
- Revision Requested context

Do not assume C2 `stage_context` is client-safe merely because it describes Waiting for Recording. If you expose Waiting-for-Recording context, explicitly document that only that specific context is client-facing and prove Revision Requested/internal context can never leak. Otherwise use a generic recording-request label and the minimum safe Content context supported by current product evidence.

## Upload Protocol and B5 Reuse

C4 should reuse the strongest existing B5 reserve -> R2 put -> finalize Ready -> activity protocol and its recovery fencing rather than fork it into weaker Content-only code.

Requirements remain:

- server-owned fresh opaque object key per upload generation
- UUIDv4 creation/retry identity
- immutable initial File facts
- exact filename/MIME/size validation
- D1 reservation before normal Ready state
- R2 write evidence before Ready
- strict generation/revision fencing
- one semantic FILE_UPLOADED event only after Ready
- incompatible request-key reuse conflicts
- response-loss retry converges
- failed/expired Uploading work can recover with a fresh key
- late old writers/finalizers cannot win
- uncertain D1 outcomes never justify blind deletion
- cleanup stays bounded and best effort
- archive remains terminal metadata behavior and does not pretend bytes were hard-deleted

If shared helpers are refactored out of the B5 Project path, prove B5 behavior is byte-for-byte or semantically unchanged through regressions.

## Recording Size and Worker Limits

The existing B5 `assets` schema deliberately caps Files at 5 MiB and requires server SHA-256. Typical recordings may exceed that.

Do not silently raise the limit, trust caller hashes, buffer an unbounded request, or rebuild canonical B5 tables casually.

Before choosing C4 size behavior:

1. inspect the committed `assets` CHECK, upload implementation, Worker request/memory limits and R2 API available in the current compatibility date
2. determine whether a larger bounded streaming protocol can still use canonical `assets`, strong integrity evidence and recoverable generations without weakening B5
3. if a safe larger-file extension truly requires a schema change or table rebuild, keep the change narrowly justified and prove preservation of all B5 rows, indexes, triggers, foreign keys and zero-to-current behavior
4. if the repository cannot safely support larger recordings in C4 without weakening invariants, retain the 5 MiB limit and document it explicitly as a C4 operational limitation rather than inventing unsafe pseudo-streaming

Do not add third-party upload services or public presigned URLs merely to bypass this constraint.

## File Validation

Retain or strengthen B5 validation:

- display filename NFC-normalized, trimmed, path/control/bidi-safe and bounded
- MIME normalized and bounded, with no authorization inferred from extension
- positive exact declared size and actual-byte agreement
- caller cannot choose R2 key, bucket, workspace, uploader, hash or Ready status
- request metadata has an exact allowlist
- incoming body handling is explicitly bounded

For Client recording uploads, do not rely on a narrow browser MIME allowlist as the security boundary. If C4 chooses a media-oriented MIME policy, make it practical for real browsers and document unknown/`application/octet-stream` handling.

No malware scanning claim unless an actual scanner is added and verified.

## Content Attachment Limits

Content asset lists must be bounded. Choose and document a deliberate per-Content cap, including archives, using current B5 and Content volume conventions.

The cap must be atomically enforced at creation and must not be bypassable by concurrent uploads.

Do not use one global low lifetime cap across all workspace Content.

## Download

Prefer extending the existing authenticated File download route so one opaque File ID resolves its attachment family internally.

For a Content-linked File, download must re-check current authorization both before and after the R2 await at least as strongly as B5:

- current active workspace/membership/identity
- current Content scope and visibility
- current Client contact when actor is Client
- File status Ready
- File visibility
- fixed Content link and current generation/revision

Missing, foreign, hidden, non-ready, archived, wrong-purpose or unauthorized cases remain leak-safe. No R2 key or storage metadata enters the response.

Use B5 safe Content-Disposition/cache/nosniff/sandbox behavior.

## Visibility, Archive and Retry

Internal Content File visibility changes and archive should reuse B5 CAS/activity behavior, capped by current Content access.

Client C4 behavior should be narrower:

- upload eligible recording
- retry that eligible recording when the canonical File lifecycle permits it
- read/download currently visible Ready recordings when allowed

Do not give Clients arbitrary visibility changes, general archive authority or access to internal assets.

A Content link never changes during visibility/archive/retry.

## Activity and History

Reuse canonical File activity where possible rather than creating duplicate Content upload events.

At minimum successful readiness remains one `FILE_UPLOADED` semantic event. Archive/visibility events remain the existing canonical File events if those mutations are exposed.

Content and Client internal history that includes Files must filter old events by the File's current Content-parent readability. Restricting Content or File, revoking assignment/contact, archiving, or changing membership/workspace state must remove inaccessible historical filenames immediately.

Do not expose internal File activity to the Client portal in C4.

## Internal Social UX

Add a real Assets/Recordings section to Content detail without turning Content into a generic file manager.

Minimum internal UX:

- list current readable Content Files with purpose, filename, size, readiness and visibility

Preserve A11/B7/C1-C3 hardening:

- real session identity
- Origin on mutations

- exact body/header/query allowlists

## Implemented C4 facts and evidence

The implementation uses additive `0016_c4_content_assets.sql`, a fixed five-column Content link with exact `recording|asset` purpose, composite workspace ownership, immutable association and mutual attachment-family exclusion. Assets and historical migrations are unchanged. The current schema has 39 domain tables and 17 domain migrations.

Content File operations share B5 storage/recovery/CAS/cleanup helpers through fixed-parent server adapters. Dedicated `content.file.manage` permits scoped Team fulfillment without changing B5 permissions. Every Client recording action uses current contact, shared Content, recording flag, Waiting for Recording and canonical Social-parent eligibility. Upload visibility is server-selected; only the original uploader may retry a non-ready Client recording. Shared Ready recordings download through the existing opaque File route, with post-R2 reauthorization and no public key/URL.

The portal exception is deliberately small: conditional Home requests and one recording page, not C6 navigation. `{id,title}` is the request allowlist; title is explicitly safe in that context. `{id,filename,mimeType,byteSize,status,readyAt}` is the File allowlist. Waiting and Revision Requested context both stay private. No other editorial, internal identity/activity, revision or storage-authority fields reach the Client.

The bounded B5 protocol and unchanged assets CHECK retain 5 MiB; current Worker/R2 docs/types and actual maximum-byte runtime verification support this decision. No larger unsafe buffered uploads, caller hashes, scanner claim or third-party storage was introduced. Content lifetime capacity is 200 including archives, atomically reserved. Request/list/history/calendar rendering is SQL-only and bounded. Canonical File events do not update Content or C3 facts; both history surfaces filter current File+Content readability.

Historical C4 tests, runtime/browser commands, counts, dependency comparison and local evidence limitations are in the C4 section of `BUILD_STATE.md`. At that handoff, advisories matched the contemporaneous exact C3 base: 53 total, zero delta.
