## Exact scope

E1 owns an internal, read-only Ads overview: scoped Campaign work list, Client/Service/Project-status filters, canonical progress/attention, forward Deliverables, pagination, safe empty/error states and links to existing Work operations.

E1 adds **no schema, migration, write endpoint, Campaign entity, stored counter, lifecycle, assignment type, activity type, provider fact, Content change, approval action, asset version, metric, portal surface or template**. It must perform no request-time repair, seed, R2 lookup or background job. Create/edit operations, when linked, remain canonical Work operations with their current authorization.

## Eligibility and live authorization

An eligible Project has a current same-workspace/same-Client Service whose Service Type points to the department with slug `ads`. Implement a relational SQL predicate, following the existing Systems precedent. Do not test labels, assume the service-type slug is `ads`, use a Project's department metadata or infer eligibility from Content.

Every Project read combines that eligibility predicate with `projectReadCondition(actor)`. Reuse canonical Work summaries and Deliverable predicates, including each child's current visibility. Keep authorization in SQL before ordering, pagination, facets, counts and overflow. The server shell or department navigation never grants data access.

- Owner/Admin/PM/Team behavior remains exactly Work behavior, including explicit Project assignment for restricted work where currently required.
- A Client or foreign, suspended, revoked or stale acting membership receives no internal Ads data.
- Client/Service assignments grant only their existing scope. Project-only scope grants minimal Client/Service display context and canonical Project access, not parent management links or siblings.
- Department membership, Project ownership and Action-only assignment cannot produce Ads parent rows or facets.
- Recheck current eligibility and access for every constituent query, including selected filter validation. A previously loaded actor is not an authorization snapshot.
- Client/Service completion and catalog active flags do not change Project lifecycle or silently remove readable work. A service-type department change does change Ads eligibility.

## Read contract and bounds

Use the existing Systems overview's bounded Work read pattern. Avoid copying a second Project/Action/Deliverable engine or broadly refactoring shared authorization merely to change a department filter.

| Input/output | Contract |
| --- | --- |
| Query keys | Exactly `clientId`, `serviceEngagementId`, `status`, `page`; scalar strings only |
| IDs | Empty or at most 200 characters; reject control/whitespace abuse using the existing Systems validation convention |
| Status | `active` by default, `all`, or an exact canonical Project status |
| Active | Excludes Completed, Cancelled and Archived; describes delivery work, not provider operation |
| Page | Canonical positive decimal integer, 1–10000; default 1 |
| Project rows | 50 readable rows plus one readable-only overflow probe |
| Ordering | Canonical attention priority, target date null last, name and ID; closed Projects gain no attention reason |
| Facets | At most 200 readable choices each, with overflow; preserve one separately authorized selected value beyond the cap |
| Service choices | Scoped to readable eligible Projects; selected Client narrows Service choices |
| Forward Deliverables | Existing six-row Work projection and readable-only overflow across the entire selected Project set, independently of the Project page |
| Delivery dates | Reuse the canonical review/approved/14-day window and each Client's timezone fallback rules |

Unknown/duplicate/array keys, invalid status/page, missing/foreign/revoked/incompatible selected IDs produce the same generic recoverable invalid-filter result. Do not silently ignore an invalid filter and show broader work. No hidden work contributes facet choices, totals, attention, progress, overflow or existence hints. Large assignment scopes use relational predicates rather than unbounded ID parameter lists. Reads remain bounded and introduce no per-row database/API/R2 calls.

## Interface

Use the existing internal shell, dynamic server rendering and Bloom primitives. Head the page **Ads** and the list **Campaign work**. Explain briefly that these are delivery Projects under Ads services. Label lifecycle filters **Project status** and use **Open projects** for the default filter rather than implying ads are running.

Each row links to the existing Project detail and shows readable Client/Service context, Project status/health, attention/target date and canonical Work summary. Use compact, distinct metadata presentation rather than dot-separated operational strings. Keep platform icons absent until there is a real platform field.

An authorized coordinator may use the existing “Create project in Work” link; the Work form owns Client/Service selection and create authority. Empty-state guidance explains that a Project must be tied to an Ads service to appear here. Team Members must not see a misleading create affordance. Filters, previous/next navigation and recoverable errors must work on keyboard and mobile.

Forward Deliverables use existing delivery labels and Work detail links. No E1 text describes Client Review/Approved as a recorded client response. No placeholder Creative/Approvals/Performance tabs, provider launch buttons, fake metrics or new portal navigation.
