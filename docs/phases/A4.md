# A4 — Authorization Layer

## Objective

Create centralized server-side authorization before feature depth increases.

Read `docs/DOMAIN_MODEL.md`.

## Authorization Layers

Identity
→ Workspace Membership
→ Role
→ Scope
→ Visibility
→ Capability

Conceptual helpers may resemble:

- requireUser
- requireWorkspaceMembership
- authorize

Implementation naming is flexible.

## Required Checks

Protected requests should verify as applicable:

1. authenticated user
2. active workspace membership
3. resource belongs to workspace
4. role may perform action
5. assignment scope permits resource
6. visibility permits access
7. special capability permits sensitive area

Default deny.

## Initial Capabilities

At minimum reserve/support:

- members.manage
- workspace.settings
- templates.manage
- finance.view
- finance.edit

Finance is not built in Release A, but capability modeling should not require later role redesign.

## Scope Rules

- Department membership does not grant every client.
- Team Member access should become assignment-based.
- Client access must remain within their own client-facing records.
- Prefer not-found behavior when revealing inaccessible resource existence would leak information.

## Verification Matrix

Explicitly test Owner, Admin, Project Manager, Team Member, and Client.

Include denied cases.

Do not rely on hidden navigation as security.

## Scope Boundary

Do not combine this phase with a large Clients feature build.
