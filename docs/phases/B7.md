## Core Rule

B7 is a hardening phase, not a feature phase.

Do not invent new workflows, lifecycle states, dashboards, assignment systems, approval systems, comments, notifications, specialist pipelines, templates, automations, Finance behavior or Release C+ placeholders.

Every code change must be justified by a reproduced defect, a violated documented invariant, or a concrete release-level acceptance gap. Prefer tests-only changes when the implementation is already correct.

## Release B Invariants To Attack

### Identity, role, scope and visibility

Preserve `Identity -> Role -> Scope -> Visibility` everywhere.

Attack at least:

- cross-workspace IDs and guessed IDs
- stale sessions after membership suspension/removal
- role changes after session issuance
- workspace suspension
- Client contact unlinking
- Client, Service and Project assignment revocation
- Team Action-only assignment and reassignment away
- Department membership as a non-grant
- Project ownership as a non-grant
- restricted Project/Milestone/Action/Deliverable/File visibility
- PM/Team explicit Project-assignment requirements for restricted work
- hidden-child counts, percentages, history, recent output and empty-state leakage
- parent readability never widening child readability
- child assignment never widening parent/sibling scope

All authorization must be based on current database truth at read time and inside committing writes where the domain already requires it.

### Projects

Attack B1 lifecycle, health independence, ownership/assignment semantics, same-workspace/same-Client Service binding, Waiting/Blocked reasons, completion/archive behavior, revision conflicts, create retries and immutable activity.

No B7 change may make Project status a derived copy of child state or automatically mutate Client, Service, Onboarding, Milestone, Action, Deliverable or File lifecycle.

### Milestones

Attack B2 lifecycle, Waiting explanations, terminal states, position uniqueness, reorder concurrency, hidden-row ordering behavior, progress derivation, retry keys, current visibility and Project-capped scope.

No automatic Project completion or template generation.

### Actions and dependencies

Attack B3 lifecycle, assignee scope, Waiting context, priority/due dates, Client-local Today/Upcoming/Overdue behavior, dependency-blocked overdue exclusion and activity filtering.

Adversarially test dependency graph integrity:

- self edges
- duplicate edges
- cross-workspace/cross-Project edges
- hidden/guessed endpoints
- two-node and longer cycles
- concurrent cycle additions
- add/remove races
- status/dependency races
- Done versus Cancelled prerequisite semantics

Cycle prevention must remain correct both in application commit paths and database constraints/triggers where implemented. Dependency blocking remains derived and never becomes a second Action lifecycle fact.

### Deliverables

Attack B4 exact lifecycle, terminal Delivered/Cancelled behavior, server-owned delivered timestamp, current visibility, Client-safe labels/status, Project cap, Team read-only behavior, retry keys, stale revisions and atomic activity.

Clients must never receive internal title/description, revision, identities, hidden counts, Service/Department IDs or internal activity.

### Files and R2

Attack the complete B5 D1/R2 boundary.

At minimum cover:

- Project/Deliverable parent authorization
- Client visibility through every parent ceiling
- guessed File IDs and object-key non-disclosure
- upload metadata validation and the 5 MiB limit
- request-key retry convergence
- incompatible retry conflicts
- fresh opaque object key per recovery generation
- five-minute lease rules
- late old writers/cleaners after recovery
- response-loss finalization
- D1/R2 disagreement
- R2 missing object behavior
- cleanup safety under uncertain database state
- archive terminal behavior and retained Ready bytes
- visibility/revision races
- direct download reauthorization after the R2 await
- safe download headers/filenames
- no storage key/hash/etag/lease/uploader leakage
- no R2 reads merely to render Work/Home summaries

Do not add malware scanning, multipart upload, retention/purge policy, relinking or new attachment subject types in B7.

### Work and Home projections

Attack B6 as read-only canonical composition.

Verify:

- Home sections are bounded and deterministic
- Work retains the canonical seven Action views and filters
- Client-local date and DST behavior remain exact
- dependency-blocked work remains excluded from ordinary Overdue
- Project attention is derived only, never stored
- closed Projects do not appear as needing attention
- hidden children do not affect counts, percentages, ordering, overflow or empty decisions
- Action-only Team assignment exposes only the Action and minimal safe parent context
- recent output uses current readable records, not stale activity titles
- archived/hidden Files disappear from current/recent summaries as defined
- dashboard reads write nothing and do not touch R2
- large assignment scope stays within D1 binding and SQL-size limits

## Concurrency And Retry Matrix

B7 must deliberately overlap operations that can race. Use real D1/workerd harnesses where practical, not only mocked sequencing.

Cover representative races across B1-B5:

- identical create retries
- incompatible same-request creates
- edit/edit stale revisions
- edit/status races
- status/status races
- reassignment versus Team progress
- scope/visibility revocation during a committing mutation
- Milestone reorder versus reorder/status/create
- dependency add/add, add/remove and cycle races
- Deliverable transitions and edits
- File reserve/finalize/recover/archive/visibility races
- late activity failure rollback

Winning facts and significant activity must remain atomic. Losers and idempotent retries must not append duplicate semantic history.

## Activity And Historical Visibility

Attack `activity_events` as immutable significant history.

Verify that Project, Client and other internal history projections re-check current readability of child subjects. Restricting, reassigning or hiding a current record must remove historical titles/details from actors who no longer have access.

Clients must not acquire internal Action, Deliverable or File activity merely because a parent is client-visible.

No B7 fix may make mutable operational state live inside activity metadata.

## Release-Level Acceptance Story

Prove a real local end-to-end Release B story using canonical operations and the actual Worker/database/storage stack:

1. Start with an activated/onboarded multi-service Client.
2. Create service-specific and Client-level Projects.
3. Add Milestones with ordering and progress.
4. Add assigned Actions, Waiting/Review states and dependency chains.
5. Add client-facing Deliverables with internal and Client-visible variants.
6. Upload Project and Deliverable Files through the real local R2 path.
7. Show Owner/Admin/PM useful Home and Work projections.
8. Show a scoped Team Member only their canonical assignment scope, including an Action-only case that does not expand parent/sibling visibility.
9. Show a Client only explicitly Client-visible Projects/Milestones/Deliverables/Files through exact safe DTOs.
10. Revoke/restrict assignments and visibility while sessions remain issued, then prove reads, counts, history and downloads shrink immediately.
11. Exercise at least one dependency race, one ordinary revision race and one File recovery/finalization race.
12. Confirm all parent/child lifecycle facts remain canonical and no dashboard/read operation mutates state.

The acceptance story must run without production, real Client data, real email, DNS changes or Leadsthatbloom access.

## Security And HTTP Hardening

Re-run and extend adversarial HTTP coverage for all Release B protected surfaces.

Verify:

- real session identity
- live membership/workspace checks
- Origin protection on mutations
- exact body/query allowlists
- malformed JSON and non-object rejection
- safe 400/401/403/404/409/500 mapping
- no raw SQL, stack, constraint, internal ID or storage authority leakage
- `no-store` on protected data and downloads as required
- guessed/foreign IDs fail leak-safely
- no browser or middleware path creates an authorization exception

Do not weaken an existing denial merely to make a UI flow easier.

## Performance And Bounds

Attack the product near its documented bounded limits and the intended approximately-ten-client operating scale.

At minimum verify:

- 200-row Project/Milestone/Action/Deliverable/File bounds where defined
- pagination and overflow truth are based on readable rows only
- hundreds of assignments do not create oversized bind lists
- Home remains bounded
- no accidental N+1 explosion across Project summaries
- no R2 listing/object scan for ordinary dashboards

Any new bound must be evidence-backed and documented, not invented for convenience.
