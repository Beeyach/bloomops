# A10 — Client Onboarding Portal

## Objective

Deliver the first complete client-facing BloomOps experience.

Read:

- `docs/PRODUCT_SPEC.md`
- `docs/DOMAIN_MODEL.md`

## Portal Home

Client sees:

- greeting
- onboarding progress
- requirements that need attention
- calm, plain-language instructions

Do not expose internal team tasks, unrelated services, restricted data, or other clients.

## Onboarding Item Types

Release A may support interactions such as:

- confirmation
- file upload
- instructions
- external link
- internal verification

## Verification Flow

Some items may require team confirmation.

Example:

Client marks Meta access sent
→ item becomes submitted/awaiting verification
→ authorized team member verifies
→ item becomes Completed

Do not blindly trust client completion for items configured as verification-required.

## Completion Rule

Onboarding can complete when every required item is:

- Completed
- Waived
- Not Applicable

Authorized override, if supported, requires a reason and activity trail.

When onboarding completes, Client may move to Active according to lifecycle rules.

## Files

If Release A file upload is included here, use the isolated R2 foundation.

Do not store raw platform passwords.

## Security Verification

Test:

- Client A cannot read Client B onboarding by ID manipulation
- Client sees only client-visible items
- internal-only notes/files are absent from client API payloads
- verification-only items require team action
- progress calculation is correct
- refresh preserves state
- completion transitions lifecycle correctly

## UX Verification

Test desktop and mobile.

Client experience should be simple enough for non-technical users.

If phase scope becomes too large, split implementation into portal display, interactions, and verification/completion subphases without crossing into Release B.
