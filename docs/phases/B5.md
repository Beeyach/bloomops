## Canonical Storage Model

D1 owns metadata and authorization facts. R2 owns object bytes.

Use the current repository's actual R2 binding and environment conventions after preflight. Do not create a new bucket, rename bindings, change production resources, or hard-code the known staging bucket name into domain logic.

The canonical File/Asset row should use the smallest coherent set of fields such as:

- id
- workspace id
- server-generated R2 object key
- original filename
- MIME/content type
- byte size
- uploader membership id
- status
- visibility
- optional failure/recovery metadata only if required for a safe lifecycle
- created/updated timestamps
- ready/archived timestamps where useful

Canonical storage states:

- Uploading
- Ready
- Failed
- Archived

Use lowercase database values if consistent with the repository.

`Ready` means D1 metadata and the expected R2 object agree enough for normal reads. `Failed` means an upload/finalization attempt did not produce a usable ready object. `Archived` removes the file from ordinary active views/downloads without pretending the bytes never existed.

Do not store file bytes, credentials, signed URLs, or raw secret material in D1.

## R2 Object Keys

R2 keys are server-owned opaque storage identifiers, never derived only from a user filename.

A safe key should be collision-resistant and workspace-separated. Preserve the original display filename separately in metadata.

Clients and internal users must never be able to choose an arbitrary R2 key, bucket, workspace prefix, or object path.

Download authorization must resolve a D1 File row first, then use that row's canonical object key. Never accept an R2 key directly from a route parameter and treat it as authorization.

## Attachment Links

Use a relational link model comparable to `asset_links` so one File can be attached to an implemented subject without duplicating file metadata.

B5 only needs attachment types that are real now, such as:

- Client
- Project
- Milestone
- Action
- Deliverable
- onboarding item/instance only if current B5 UI and authorization can support it coherently without widening A10 semantics

Do not add future Content, Request, Page, Finance, or specialist subject types merely because the durable model mentions them for later releases.

A link must remain in the same workspace and, where the subject belongs to a Client/Project tree, must not cross Client/Project boundaries.

Prefer database-backed relationship checks where relational FKs are possible. For polymorphic links, prove subject existence and same-workspace ownership in committing code and tests. Guessed subject ids must fail without leaking existence.

## Visibility and Authorization

Preserve `Identity -> Role -> Scope -> Visibility`.

Visibility values:

- Internal
- Client
- Restricted

Owner/Admin may coordinate Files across their workspace scope. Project Manager may coordinate Files only where the linked subject is within the Project/Client/Service scope already granted by the canonical parent rules. Team Member access is read-only or upload-capable only when the exact linked subject is already readable and the phase implementation gives that operation explicitly; Department membership and ownership fields never grant access.

Restricted Files require the same explicit restricted-parent/project assignment behavior already established by B1-B4. A File must never widen the visibility or scope of its linked subject. The effective permission is the intersection of File visibility and every parent/subject rule needed to reach it.

Clients may see/download only Ready, Client-visible Files linked to their own currently reachable Client-visible subjects. Internal or Restricted Files never enter Client rows, counts, activity, filenames, MIME details, or guessed-id responses.

A Client-visible File attached to an Internal/Restricted Project, Deliverable, Milestone, or other parent must remain hidden because the parent caps the child.

## Upload Flow

Use the simplest safe flow compatible with the existing Worker and R2 binding.

The design must explicitly handle the fact that D1 and R2 are not one atomic transaction.

A coherent pattern is:

1. authorize the subject and intended File visibility
2. validate filename, size, content type, and request id
3. create/reserve D1 metadata in `Uploading` with a server-generated object key
4. write the object to R2
5. finalize the same File row to `Ready` only after the object write succeeds and canonical metadata agrees
6. record significant activity exactly once for the successful ready File
7. if the object write or finalization fails, transition or recover the row safely as `Failed` and clean orphaned object bytes when possible

Codex may choose a different sequence only if it proves equal or stronger recovery guarantees.

Creation/upload retries must converge on the same logical File when the same retry key and immutable initial request details are reused. Reusing a key with incompatible details must conflict.

Never create two Ready metadata rows or two semantic upload events for one response-loss retry.

## Upload Validation

Preflight the actual Worker/platform request limits and existing app conventions before choosing a B5 maximum size. Pick a deliberate bounded maximum and document it.

At minimum validate:

- non-empty safe display filename with bounded length
- positive bounded byte size
- body length and declared metadata agreement where available
- bounded MIME/content type text
- no control-character filenames
- no caller-provided object key or workspace id

Do not rely on filename extension for authorization or trust.

Do not claim malware scanning if none exists.

## Download Flow

Download routes must:

- require real session identity
- resolve File metadata by opaque File id
- recheck current workspace membership, linked-subject scope, parent visibility, and File visibility at request time
- require `Ready` status
- fetch the canonical R2 key from metadata only
- return safe headers
- avoid exposing internal R2 keys, bucket names, credentials, or stack/constraint details
- use an attachment-safe Content-Disposition filename
- protect cache behavior for authenticated/private resources

A missing metadata row, hidden File, foreign workspace File, hidden parent, archived/failed/uploading File, or missing R2 object must not leak sensitive existence information.

If metadata says Ready but the R2 object is unexpectedly missing, fail safely and record/recover only if the repository's activity/error conventions support it without mutating on ordinary reads unexpectedly.

## Archive and Cleanup

B5 should support a deliberate archive/remove-from-active-use operation if needed by the product surface.

Archiving is a metadata lifecycle change, not a promise of immediate hard deletion. Do not build destructive purge retention policy in B5 unless the existing product specification already requires it.

If upload failure leaves an object that should not remain, attempt safe cleanup. Cleanup failure must not turn a failed upload into Ready.

No production bucket cleanup or destructive sweeping is allowed in implementation verification.

## Activity

Use canonical `activity_events` for significant File facts.

At minimum distinguish:

- FILE_UPLOADED / FILE_READY equivalent
- FILE_ARCHIVED if archive exists
- FILE_LINKED / FILE_UNLINKED only if links are mutable and the distinction matters

Choose one canonical event for successful upload readiness rather than recording duplicate semantic events for reserve and finalize steps.

Activity must not expose R2 keys, hidden parent titles, secret bucket metadata, or internal-only filenames to actors who cannot currently read the File.

Project/Client history projections that include Files must filter by current File plus parent readability so historical names do not leak after restriction or unlinking.

Clients do not receive internal File activity in B5 unless there is an existing dedicated safe Client activity projection contract that explicitly allows a client-safe File event. Prefer no Client File history for B5 if uncertain.

## UI

Build the smallest useful Files experience without generic dashboard clutter.

Internal Project detail should show Files only when implemented records exist or as a functional section with authorized upload, download, visibility and attachment behavior.

Deliverable detail/Project Deliverables may surface attached Files if the relationship is clear and B5-safe. Do not invent versioning or approval controls.

Client portal may show Client-visible Ready Files under reachable Projects/Deliverables or a conditional Files area only when real visible Files exist. Do not expose empty future navigation destinations.

File rows should make filename, size, type/status, uploader/date context where safe, and download action understandable. Use existing Bloom primitives and responsive patterns.

Upload controls must be keyboard accessible, have clear pending/error/success behavior, and remain safe before hydration like B3 controls.

## API Hardening

Preserve A11/B1-B4 rules:

- real authenticated sessions
- Origin checks on mutations
- strict request/body parsing
- exact authority field allowlists
- safe 400/403/404/409/413/500 responses as appropriate
- `no-store` on protected metadata responses
- sanitized errors
- guessed/foreign ids fail closed
- no raw database rows or R2 keys at UI/portal boundaries

File byte responses may use appropriate authenticated cache headers, but must not accidentally become public shared-cache objects.

## Security and Failure Verification

Test at minimum:

- Workspace A cannot read/upload/download/link/archive Workspace B Files
- Client cannot guess internal/restricted File ids
- Client-visible File remains hidden if its parent subject is not Client-visible
- Team/PM scope follows existing Client/Service/Project rules
- Action-only assignment does not automatically expose unrelated Project/Deliverable Files
- Department membership and Project ownership grant nothing
- stale membership/workspace/role/contact/assignment/visibility revocation applies to metadata and byte downloads
- caller cannot choose R2 object keys or overwrite another File's bytes
- duplicate request retry converges without duplicate Ready rows/events
- incompatible retry-key reuse conflicts
- R2 put failure never produces Ready metadata
- D1 finalize failure does not silently produce a Ready File and has safe orphan cleanup/recovery behavior
- cleanup failure remains safe
- missing R2 object behind Ready metadata returns a sanitized failure
- archived/failed/uploading rows cannot download
- same-workspace attachment rules hold for Project/Milestone/Action/Deliverable/Client subjects implemented in B5
- guessed/foreign attachment targets fail without existence leaks
- link/unlink retries and concurrent mutations are coherent if link mutation is exposed
- filename/header injection attempts are neutralized
- MIME and size validation are bounded
- large scoped lists remain below D1 bind limits
- no parent lifecycle is mutated
- no Client portal raw keys, hidden counts, uploader identities, or internal-only metadata leaks

## Acceptance Story

Prove at least one end-to-end B5 story against the real local Worker/D1/R2-compatible environment:

1. An authorized coordinator opens an existing B4 Project/Deliverable and uploads a bounded file.
2. The File moves through the intended upload lifecycle and becomes Ready only after the object exists.
3. A response-loss retry converges on the same File without duplicate bytes/semantic history.
4. Internal and restricted Files stay hidden from unauthorized Team/PM/Client actors.
5. A Client-visible File under a Client-visible parent can be downloaded by the linked Client, with only safe metadata exposed.
6. Hiding/restricting the File or parent, unlinking the Client contact, or suspending membership revokes access immediately, including byte download.
7. Simulated R2/D1 failures leave a recoverable Failed/non-ready state and no false Ready record.
8. No Project/Milestone/Action/Deliverable/Client lifecycle changes because of File operations.

## Exit Criteria

B5 is complete only when D1 metadata, R2 object ownership, upload/finalize/recovery, attachment links, visibility, authorization, download, activity, UI, and tenant isolation are coherent; all prior regressions remain green; migration/Worker/R2/browser gates pass; docs describe exact implemented behavior and limits; and the temporary Codex prompt has no net diff.

Do not claim B6 Work + Home Projections or B7 hardening is complete.

Independent audit, user-controlled merge and both gates on the eventual B5 merge SHA remain required.

B5 uses additive `0012_b5_files.sql`: `assets`, `asset_links` and durable `asset_upload_attempts`, plus the composite Deliverable identity index. The scope is fixed Project and Deliverable attachments, a 5 MiB maximum, 200 Files per Project including archives, coordinator-only upload/retry/visibility/archive, and Team read-only access. There is no generic Client/Milestone/Action/onboarding attachment endpoint or mutable relinking. These choices match the current Project/Deliverable UI and preserve the exact parent permission ceiling; later attachment integrations need their own coherent workflow.

Every recovery generation gets a fresh server-owned key. D1 reserve and Ready/activity batches recheck live authorization. Positive R2 size/MIME/etag/SHA-256 evidence precedes Ready; uncertain D1 outcomes do not justify blind cleanup. Failed or expired Uploading work can be explicitly retried; old known keys remain recoverable and cleanup is bounded and best effort. Archive retains previously Ready bytes. The six-field Client DTO and authenticated attachment downloads exclude storage authority and internal history.

The final model, protocol, runtime evidence, exact checks, changed paths and deliberate limits are recorded in `DOMAIN_MODEL.md` and `BUILD_STATE.md`. B6 and all later work remain unimplemented.
