# A5 — New BloomOps Shell

## Objective

Make BloomOps structurally and visually stop being a prospecting application without yet building the full product.

Read `docs/PRODUCT_SPEC.md`.

## Architecture

Move away from the inherited giant `ProspectsApp.jsx` shell.

Use route-based application areas with shared layouts.

Internal shell conceptually owns:

- navigation
- current user/workspace
- account menu
- theme
- dialogs
- toasts

Individual product areas own their own routes and data.

## Internal Navigation

Target destinations:

- Home
- Clients
- Onboarding
- Work
- Social
- Ads
- Systems
- Pages
- Team
- Finance
- Settings

In Release A, only:

- Home
- Clients
- Onboarding
- Team
- Settings

need meaningful functionality.

Other destinations may be deliberate placeholders.

Do not create fake features.

## Client Shell

Use a separate portal layout.

Client should not see an internal sidebar with hidden items.

Release A portal may initially contain only:

- Home
- account/sign out

Later portal sections appear only when applicable.

## Reuse

Preserve useful generic inherited UI:

- theme
- icons
- dialogs
- toasts
- inputs
- selects
- loading/error patterns
- responsive behavior

Do not redesign the entire component system in A5.

## Verification

- internal user lands on internal Home
- client lands on Portal
- client cannot render internal shell
- internal user does not accidentally use client shell
- prospecting navigation is no longer the BloomOps primary shell
- Pages/editor generic code remains intact

## Scope Boundary

Do not build full Clients, Onboarding, Social, Ads, or Systems features here.
