# C5 - Approvals + Revision History

Add formal, append-only Client approval rounds and durable Content review revisions on top of the C1-C4 Social model. C5 must preserve what was actually sent for review and how the Client responded, without turning activity metadata into mutable state, without overwriting earlier rounds, and without building the general C6 Client Content portal.

## Durable Model Direction

The domain model requires approval history to be append-only by round. C5 should implement the smallest Content-specific relational model that makes that true.

Expected conceptual records:

### Content review revisions

An immutable review revision represents the exact Client-review package at the moment approval is requested.

It should include, directly or in one exact validated JSON snapshot:

- workspace
- Content Item id
- revision/sequence number for review history
- immutable snapshot of the reviewable Content fields
- immutable platform/date presentation needed to understand what was reviewed
- creator/requester provenance
- created timestamp

Do not reuse the mutable `content_items.revision` CAS integer as the durable review revision identity. CAS revision and Client review revision are different concepts.

Prefer an exact allowlisted snapshot over copying internal database rows wholesale. Never snapshot storage keys, hashes, uploader internals, owner identities, assignment internals, activity internals, arbitrary HTML, or hidden fields merely because they exist on Content.

### Content approval rounds

Each formal approval round belongs to exactly one Content Item and exactly one immutable review revision.

Canonical statuses from the domain model:

- Requested
- Approved
- Changes Requested
- Withdrawn

Store the smallest coherent facts, conceptually including:

- workspace
- Content Item
- round number
- review revision id
- requested by
- status
- bounded feedback when applicable
- responder identity when a response occurs
- requested/responded/withdrawn timestamps as needed

Prior rounds and prior revision snapshots are immutable. Never update round 1 into round 2, never overwrite prior feedback, and never make the activity log the only place the old response exists.

## Review Snapshot Safety

Requesting approval is an explicit act that may expose a bounded review package to currently linked Client contacts. This is stronger than ordinary Content `visibility=client`, but it still must not expose every internal Content field.

Inspect current product wording and C1-C4 fields before finalizing the exact snapshot. The safe default review package should be limited to fields a Client genuinely needs to approve the Content, such as appropriate combinations of:

- title
- Content type
- hook
- script/body copy
- caption
- CTA
- target publish date
- platform labels

Treat internal pillar/classification, owner, assignment, revision/CAS values, workflow internals, activity metadata, private stage context, hidden File counts and storage metadata as private unless exact repository evidence says otherwise.

C6 later owns the general Content portal. A review snapshot being Client-visible does not make the live Content row or unrelated fields Client-readable.

## Approval Request Lifecycle

C5 must integrate with C2 without duplicating stage state.

A formal approval request is valid only when all current facts support Client review, including at minimum:

- Content is currently readable/manageable by the internal actor
- Content `client_approval_required = true`
- Content stage is `client_review`
- no other Requested approval round is open for that Content
- current Content parent Client/optional Social Service remains valid
- current Content visibility and actor scope permit the operation

On request:

1. capture one immutable review revision from current canonical Content/platform/date facts
2. allocate the next round number atomically
3. create one Requested approval round referencing that revision
4. append one semantic approval-request activity fact
5. preserve the current Content stage as `client_review`

All of those facts must commit atomically or not at all.

Do not create a revision snapshot merely because a page renders. Do not create duplicate snapshots/rounds on response-loss retry.

If exact implementation evidence shows creating the round directly as part of the C2 transition into `client_review` is safer, that is acceptable only if legacy/existing Client Review rows remain handleable and all C2 regressions stay green. Prefer the simpler explicit request operation unless integration evidence clearly favors another design.

## Editorial Freeze During Requested Review

A Requested round represents a fixed package. While a Requested approval round is open, mutations that would make that package stale must not silently change what the Client is being asked to approve.

At minimum, block or otherwise safely fence mutations to the fields represented in the review snapshot, including relevant platform/date changes, until the Requested round is resolved or withdrawn.

Do not silently rewrite the immutable snapshot to match later edits.

Visibility, membership/contact and assignment facts remain live authorization facts. Revoking access must hide/fence the round immediately; it does not rewrite historical records.

## Client Approval Response

C5 introduces only the minimum Client approval write path.

A Client may respond only when all current facts prove:

- authenticated active Client membership in the same active workspace
- current `client_contacts.user_id` linkage to the exact Content Client
- Content remains Client-visible and in the exact parent scope
- optional Service is still the canonical same-Client Social service when service-bound
- the approval round is currently Requested
- the Content is still in `client_review`
- the round references an immutable review revision for that same Content/workspace

The response body must be exact and bounded.

### Approve

A valid Client approval should atomically:

- mark the Requested round Approved
- record responder and response timestamp
- move Content from `client_review` to `approved` using the same strict current-revision/current-stage authorization guarantees as C2
- append the semantic approval response and Content stage facts without duplicate history

Do not let the Client call the generic C2 transition endpoint.

### Changes Requested

A valid Client changes-requested response must require bounded non-empty feedback and atomically:

- mark the Requested round Changes Requested
- store immutable feedback on that round
- record responder and response timestamp
- move Content from `client_review` to `revision_requested`
- set the current C2 revision-request context from the bounded Client feedback if the current pipeline contract requires stage context
- append semantic approval/stage history exactly once

The immutable round feedback is the durable historical source. Current `stage_context` remains only the operational current-state context.

## Coordinator Withdraw

An authorized internal coordinator may withdraw a currently Requested approval round when the review should no longer be active.

Withdrawal must:

- preserve the immutable review revision and round record
- mark only the current Requested round Withdrawn
- record who withdrew it and when, plus a bounded reason if implemented
- append one semantic activity fact

Prefer leaving Content in `client_review` after withdrawal so the coordinator can edit and submit a fresh round. If exact C2 constraints make that unsafe, document and prove the chosen stage behavior rather than adding a broad new back-navigation system.

## Interaction With C2 Stage Controls

C5 must prevent formal approval from being bypassed once Client approval is required.

At minimum:

- Clients never use generic stage transitions.
- A Requested approval round blocks competing stage transitions that would invalidate the round.
- For `client_approval_required=true`, direct internal `client_review -> approved` must not bypass the formal Client approval result after C5.
- `client_review -> revision_requested` while a Requested round is open must not bypass the Client response/withdraw flow.
- Internal Review -> Revision Requested remains valid internal rework.
- Revision Requested -> Editing remains the C2 rework path.
- Content with `client_approval_required=false` continues to skip Client Review according to C2.
- Published remains terminal exactly as C2 defines.

Do not add a second approval status on `content_items`.

## Round Numbering and Concurrency

Round numbers are monotonic per Content Item and allocated under concurrency.

Prove:

- two concurrent approval requests cannot both become round N
- only one Requested round may exist per Content Item at a time
- response versus response has one winner
- response versus withdraw has one winner
- response versus Content mutation has one canonical winner
- request versus Content edit/platform edit/date edit has one canonical winner
- stale page responses return safe conflict
- identical response-loss retries converge without duplicate round/revision/activity/stage events
- late failures roll back all round/revision/stage/activity facts atomically

Use existing CAS/request-id patterns where appropriate. Do not introduce a speculative global workflow engine.

## Revision History Semantics

C5 revision history is formal review history, not an audit of every keystroke.

Each requested Client review round freezes one review revision. After Changes Requested or Withdrawn, internal users may edit the live Content. The next formal request creates a new immutable review revision and a new round.

The internal Content detail should allow authorized users to understand:

- round number
- round status
- requested/responded timestamps
- bounded feedback
- the immutable review snapshot for that round
- who requested/responded where safe internally

Do not overwrite prior snapshots when live Content changes later.

## Client Read Surface

C6 owns the general Client Content portal. C5 may add only a narrow approval surface, analogous to C4's narrow recording route.

Preferred shape:

- conditional `Approval needed` module on Client Home when currently actionable Requested rounds exist
- dedicated `/portal/approvals/[roundId]` route or equivalent
- exact allowlisted approval DTO based on the immutable review revision
- Approve and Request changes controls only
- optional past-result confirmation for the Client's just-completed round if needed for response-loss UX

Do not add general `/portal/content`, Social calendar, Content search, internal activity or browsing of non-actionable Content.

Hidden/ineligible rounds must not affect counts, overflow, empty states or navigation.

## Client DTO Rules

Never expose through C5 simply because the round exists:

- Content owner or membership ids
- internal Client/Service/Department ids beyond opaque route ids required to act
- CAS revision
- internal activity
- waiting/revision internal context other than the exact immutable feedback the Client themselves submitted where needed
- internal-only Files
- R2 keys, hashes, leases, attempts or uploader internals
- hidden counts
- internal pillar/classification unless explicitly proven client-reviewable

The review snapshot must be selected from an exact allowlist. Do not serialize a raw Content row.

## Files and Preview Assets

C4 remains the canonical Content File system.

C5 must not create File versions or another blob store.

If review UX includes C4 Files, expose only currently Ready, Client-visible Content Files that are explicitly safe for the approval context and remain authorized under current C4 rules. Do not make historical bytes permanently public merely because an older revision referenced them.

If exact durable File-version semantics are not available safely, keep the formal C5 revision snapshot to structured review fields and document that limitation rather than inventing weak File versioning.

## Authorization

Preserve `Identity -> Role -> Scope -> Visibility`.

Internal:

- Owner/Admin coordinate reachable approvals.
- Project Manager follows existing C1-C4 Content scope. Restricted Content still requires exact current Client/Service assignment.
- Team Member may view review history inside current Content fulfillment scope but should not request/withdraw formal Client approval unless exact product evidence makes that responsibility appropriate. Prefer coordinator-only request/withdraw by default.
- Content owner, Department, Project and Action relationships remain non-grants.

Client:

- current contact linkage only
- exact Content Client only
- Client-visible Content only
- Requested round only for action
- no internal approval administration

Every read and write rechecks current database truth. Stale sessions do not preserve removed access.

## Activity

Use immutable significant facts. Expected semantic events may include equivalents of:

- `CONTENT_APPROVAL_REQUESTED`
- `CONTENT_APPROVAL_APPROVED`
- `CONTENT_APPROVAL_CHANGES_REQUESTED`
- `CONTENT_APPROVAL_WITHDRAWN`

If current repository conventions favor a smaller event vocabulary, document the exact mapping. Activity must not become the canonical approval record.

Current internal Client/Content history must filter approval events by current Content readability. Clients do not receive internal activity history in C5.

## API Boundary

Preserve A11/B7/C1-C4 hardening:

- real session identity
- active workspace/membership
- Origin checks on mutations
- authorization before validation where leak safety requires it
- exact JSON/query allowlists
- malformed/null/array/scalar input rejected safely
- no caller workspace/client/service authority
- safe 400/401/403/404/409/500 mapping
- `no-store` on protected metadata reads

Use dedicated approval endpoints. Do not overload the generic Content edit endpoint with approval authority.

## C5 Acceptance Story

Prove at least one integrated local story:

1. Create Client-visible Content requiring Client approval with C3 platform/date facts and C4 assets present.
2. Progress through C2 to Client Review.
3. Coordinator requests approval; one immutable review revision and round 1 are created atomically.
4. Client Home shows only the actionable approval for the linked Client.
5. Another Client, guessed id, hidden Content, wrong workspace, wrong Service or revoked contact cannot view/respond.
6. While round 1 is Requested, reviewable Content edits/platform/date mutations cannot silently invalidate the snapshot.
7. Client requests changes with bounded feedback; round 1 becomes Changes Requested and Content becomes Revision Requested exactly once.
8. Internal user returns Content to Editing, makes changes, progresses back to Client Review, and requests approval again.
9. Round 2 references a different immutable review revision while round 1 and its feedback remain unchanged.
10. Client approves round 2; Content becomes Approved exactly once.
11. Response-loss retry converges without duplicate revision, round, activity or stage events.
12. Coordinator-withdraw race versus Client response has one winner.
13. Revoking contact/assignment/Content visibility with an issued session immediately removes approval reach and fences writes.
14. C4 recording/assets and C3 calendar facts remain unchanged by approval operations.
15. No C6 general Content portal or C7 hardening work is introduced.
