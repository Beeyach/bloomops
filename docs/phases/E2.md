## Canonical identity

Preserve the E2A immutable `productionArea` (`social` or `ads`, stored as `production_area`) and nullable `adsProjectId` (`ads_project_id`) in `content_items`.

- Every existing record remains `social` with no Ads Project, including all existing `ad_creative` records. No migration reclassifies by type, name, platform or current service department.
- New Social creation explicitly supplies `social` and null Project; existing Client-level Social content remains supported.
- New Ads creation requires one canonical Project tied to a current Ads Service. Workspace, Client and Service are derived from that Project; they must match the Content row exactly. No Client-level Ads creative in E2.
- Production area, Project and existing Content identity fields stay fixed after creation. No conversion, move, reassignment or linking an old Social record into Ads. Intentional reuse can later create a new record; it cannot rewrite old provenance.
- Use the existing Content ID, editorial columns, type vocabulary, owner field, revision, stages, platform associations and activity. Default an Ads creative to `ad_creative`; type and platform remain descriptive facts, never grants or provider identities.
- Keep the existing workspace/Client/request-ID uniqueness. New creation receipts identify area and Project as well as existing normalized inputs. Old receipts without these fields mean Social/null. A reused request key with a different area or Project conflicts without exposing an unreadable conflicting record.

E2A specifies the additive migration and database integrity constraints. E2B must implement creation and retry atomically with platforms and the immutable creation event, rechecking current parent authority at commit time. It must not create a Work Project, Action, Deliverable or File merely to represent a creative.

## Internal permission contract for E2B

Every Ads creative operation proves current workspace/membership/role, exact stored parent tuple, Ads Service eligibility, Project readability and Content visibility in SQL. Department membership, Project ownership, Content ownership and Action-only assignment grant no creative access.

Owner/Admin retain their existing broad internal authority. PM retains broad access to ordinary Projects. Team scope follows current Client/Service or explicit Project assignment. A restricted Project requires explicit Project assignment for PM/Team. A restricted Ads Content item or restricted Ads File also requires explicit assignment to that Project for PM/Team. A broad Client/Service assignment must not bypass that child restriction.

Within that proven scope, internal roles may create/edit/progress Ads creative and manage its internal assets, consistent with existing Content production responsibilities. This grants no ability to create/manage the parent Project, Client or Service. Only server-loaded, typed Ads resource descriptors may admit Project-only Content scope; a caller-owned `projectId`, area or descriptor must never grant access. Preserve Social's existing Client/Service/restricted rules exactly.

Creation and visibility changes must validate both current and desired access. A Project, membership, assignment, service department or relevant visibility change revokes subsequent reads, writes, retries, history and file access, including requests using previously loaded actors. Each committing batch retains live predicates and strict revision checks. Failed/concurrent losers create no activity or partial assets.

## Routes and containment

- Existing Social list/calendar/pages and their facets remain Social-only. Existing Client/Service Content creation routes remain Social-only and reject area/Project fields in the body.
- E2B adds `/ads/creative`, `/ads/creative/new` and `/ads/creative/:contentId` with edit support. New creation is scoped to an existing Project, for example `/api/bloomops/projects/:projectId/creative`; derive the complete identity server-side.
- Reuse canonical per-Content mutation, platform and File implementations. Generic internal ID endpoints may dispatch from the stored production context once E2B supplies explicit typed authorization; generic Social collection routes never become mixed lists. Social page requests for Ads IDs return the same unavailable response as an inaccessible ID.
- Client portal Content, recording requests/uploads, approval inbox/detail/responses and their navigation remain Social-only throughout E2. Both a forged Ads visibility value and later Ads-to-Social service reclassification must still fail the explicit production-area check.
- Canonical File-family download/retry resolution must inspect the current parent context and enforce that context at every storage boundary. A Work Project link must not grant access to a sibling Content File. No automatic duplicate asset links, copied R2 objects or new File family.
- Canonical activity keeps `subject_type='content'` and the Content ID. Ads detail/history uses current Ads authorization; Client-level aggregate history may include Ads events only when its parent is independently authorized and each event is currently readable. No historical title, foreign ID, URL, storage key or hidden count leaks through retries or activity.

## Production boundary before E3

E2B begins at Idea and supports Script → Editing → Internal Review, plus Internal Review → Revision Requested → Editing with the existing bounded revision explanation. Reuse canonical stage storage and transition receipts; do not add an Ads status column.

For E2 Ads records, keep recording-required false, internal-review-required true and client-approval-required true as server-owned workflow configuration. The UI does not offer flags that bypass the review boundary. Enforce the same stage/flag rules on generic APIs and inside committing predicates, not just in transition menus.

E2 never enters Waiting for Recording, Client Review, Approved, Scheduled or Published, and never changes `publishedAt`. The internal detail view explains that client approval is a later capability; it offers no inactive approval button. Ads Content and new Ads assets are internal or restricted; E2 does not accept client visibility. Existing Social transitions, flags, publication facts, uploads and approval responses remain unchanged.

E2 assets are working media, not approved immutable versions. Existing Content/File/R2 semantics govern validation, type/size limits, hashing, upload leases, retries, revisions, visibility, archive and download. E3 must separately establish immutable media approval evidence before any UI claims approval covers an image/video asset.
