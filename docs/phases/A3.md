# A3 — Authentication and Membership

## Objective

Replace the temporary inherited access-code model with real user identity, sessions, membership, and invitations.

Read `docs/DOMAIN_MODEL.md`.

## Authentication Direction

Current intended provider: Better Auth.

Revalidate current official Better Auth + Cloudflare/D1 guidance before implementation.

Initial sign-in experience: magic link.

Transactional email provider: Resend.

## Responsibilities

Auth provider owns:

- identity
- session
- email verification
- magic-link flow

BloomOps owns:

- workspace membership
- role
- client/service scope
- capabilities

Do not let an auth-provider organization abstraction become the canonical BloomOps authorization model unless repository evidence clearly justifies it.

## Initial Roles

- Owner
- Admin
- Project Manager
- Team Member
- Client

## Membership States

- Invited
- Active
- Suspended
- Removed

Suspension must revoke workspace authorization even if a valid identity session still exists.

## First Workspace

No public agency-registration screen.

Bootstrap the first workspace intentionally.

Initial intended memberships:

- Ellen = Owner
- Ary = Admin

Do not hardcode permanent email addresses into application logic.

## Invitations

Invitation states:

- Pending
- Accepted
- Expired
- Revoked

Invitation should be tied to the intended email.

Wrong-email users must not be able to accept another person's invitation.

Resending should invalidate the old invitation token.

## Privacy

Unknown email sign-in should not reveal whether an account exists.

## Verification

Test:

- valid magic-link sign-in
- expired/invalid link
- unknown email enumeration resistance
- invitation acceptance with matching email
- wrong-email rejection
- suspended member loses access
- old Leadsthatbloom access codes no longer authenticate after cutover

## Scope Boundary

Do not build detailed Clients UI or authorization scope rules beyond what is necessary to complete auth/membership.
