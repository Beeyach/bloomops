## Canonical Content Item

Content is specialized Social production data. It is not a generic Action, Deliverable or Page.

Each Content Item belongs to exactly one workspace and one Client. It may optionally reference one Service Engagement, but that Service must:

- belong to the same workspace
- belong to the exact same Client
- resolve to the Social department through the canonical Service Type/Department relation

A null Service means Client-level Social content. Never accept caller-owned workspace/client identity through a detail edit.

Do not add speculative analytics, platform IDs, approval IDs, file IDs, project IDs, action IDs, comments, scoring, campaign fields or template metadata in C1.

## Editorial Field Validation

Validation must be explicit, normalized and bounded. Follow existing repository conventions and choose limits that are practical for real Social work.

At minimum:

- title required, trimmed, non-empty, reasonably bounded
- type exact allowlist
- pillar optional, trimmed and bounded
- hook/script/caption/CTA optional strings, normalized and individually bounded
- reject control/path/header-style abuse where relevant to the existing string helpers
- workflow flags exact booleans, never truthy coercions
- target publish date exact real calendar date or null
- owner must be a valid current internal membership of the same workspace when set
- visibility exact `internal`, `client` or `restricted`
- revision positive integer
- UUIDv4 creation request identity

Do not silently discard unknown body/query keys. Preserve the exact-input boundary established by B7.

## Responsibility And Authorization

Preserve `Identity -> Role -> Scope -> Visibility`.

Content owner is responsibility only. Department membership and owner fields never grant Content access.

### Owner / Admin

May read/create/edit reachable Content across the workspace subject to current workspace/Client/Service truth and visibility.

### Project Manager

May coordinate Content across the workspace under the existing PM model. For `restricted` Content, require an explicit current Client or Service assignment appropriate to that Content rather than treating PM workspace coordination as a restricted-record grant.

### Team Member

Social contractors must be able to do real fulfillment, but only inside existing assigned scope.

A Team Member may read/create/edit Content only when current canonical Client/Service assignment already reaches the Content parent. A Service-specific item should respect the narrower Service assignment when appropriate. Client assignment may reach that Client's Content according to the same A/B scope semantics already used elsewhere.

For `restricted` Content, PM/Team must have an explicit current Client or Service assignment to the exact parent context. Do not add a Content assignment table in C1.

Action-only assignment, Project assignment, Department membership and Content owner responsibility do not create Content scope.

### Client

No C1 internal Social access. Do not expose a Client Content API or portal DTO yet. C6 owns Client Content presentation.

### Service binding

A caller must never attach Content to a GHL, Kajabi, Ads or other non-Social service merely because they can name its ID. Validate the Service Type's canonical Department.

## Visibility

Content visibility is `internal`, `client` or `restricted`.

`client` means eligible for a later Client portal phase; it does not create Client access in C1.

Changing visibility must re-check live scope at commit time. Current restriction must immediately remove the record from PM/Team readers who lack the explicit assignment required above.

## Creation Retry

Use a UUIDv4 creation request key and immutable initial creation snapshot, following the strongest current Deliverable/File patterns where appropriate.

Requirements:

- same workspace/Client/request key plus identical normalized initial facts converges on one Content Item
- response-loss retry after later edits still returns that same item without reverting edits
- incompatible request-key reuse conflicts
- concurrent identical creates append exactly one semantic creation event
- no caller can move the item to another Client/Service/workspace through retry data

If repository evidence supports a simpler safe pattern, document it and preserve the same guarantees.

## Edits And Concurrency

Content detail edits use revision compare-and-swap.

Editable C1 fields should be only the structured non-stage fields owned by C1. Parent Client is immutable. Service binding may be fixed after creation unless repository evidence proves a safe business need to change it; prefer immutability in C1 because Service context affects scope.

Competing edits:

- one canonical winner
- stale loser returns safe conflict
- one revision increment
- one semantic activity event
- late activity/fact failure rolls back atomically

No edit changes Client, Service, Action, Deliverable, Project, File or Onboarding lifecycle.

## Activity

Record significant Content facts in immutable `activity_events` using the existing atomic fact/event conventions.

Minimum C1 events:

- `CONTENT_CREATED`
- one canonical details/configuration update event, unless repository conventions strongly justify splitting visibility from ordinary details

Creation activity should retain enough immutable normalized initial facts to prove retry compatibility, without storing secrets or becoming mutable operational state.

C1 does not need a new public/client history surface. If current internal Client history is extended, every event title/detail must be filtered by current Content readability before presentation.

## Bounded Reads

Content volume is long-lived and can exceed one campaign or month. Do not impose an arbitrary low lifetime cap per Client merely to make queries easy.

Instead:

- use deterministic bounded pages
- stable ordering
- fetch one extra readable row for truthful overflow
- hidden rows must not create false overflow
- use relational scope predicates rather than materialized huge ID lists
- keep D1 statements under existing binding/statement limits

Choose and document the page size from current repository conventions.

## API Boundary

C1 APIs must preserve A11/B7 protections:

- real session identity
- current active workspace membership
- Origin checks on mutations
- live role/scope/visibility checks
- exact query/body allowlists
- malformed/null/array/scalar JSON rejected safely
- no unknown-key silent discard
- sanitized 400/401/403/404/409/500 responses
- no SQL, stack, constraint or foreign-record leak
- `no-store` on protected data
- guessed/foreign/out-of-scope IDs fail leak-safely

Authorization should occur before input validation when changing the order would otherwise leak resource existence, matching B7's hardened Work boundary.

## C1 Acceptance Story

Prove at least one real local story:

1. Seed two Clients with multiple Service Engagements including Social and non-Social services.
2. Owner/Admin/PM create structured Content for a Social service and Client-level Social work.
3. Attempted binding to another Client, another workspace or a non-Social service fails safely.
4. A scoped Social Team Member reads/creates/edits only Content reachable through current Client/Service assignment.
5. Department membership, Content ownership, Project assignment and Action-only assignment do not widen scope.
6. Restricted Content requires the explicit current Client/Service assignment for PM/Team.
7. Creation response-loss retry converges and incompatible reuse conflicts.
8. Competing edits produce one fact/revision/event winner.
9. Revoking/suspending/reassigning while a session remains issued removes Content immediately.
10. Content stage remains Idea throughout C1 and cannot be caller-mutated.
11. No Client can reach internal C1 Social routes or a Content portal projection.
12. All reads are bounded and no C1 operation mutates Release A/B parent lifecycles.
