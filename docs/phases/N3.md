### N3B reviewed CSV (implementation decisions)

Use a bounded generic metric-row CSV, not a provider-export compatibility claim.
One file targets one saved report's exact template/version, period, timezone,
channel, account and scope. A maximum of 64KiB and the catalogue's metric count
applies. Headers map by exact named fields in any order; unknown/duplicate columns,
duplicate metric keys, wrong units/context and invalid normalized observations
reject the entire review. Omitted metrics remain untouched; values replace, never sum.

The editor downloads the current report as a reusable CSV and reviews an uploaded
file before applying selected rows to its unsaved form. Existing values/provenance
are shown alongside imports; conflicting rows default unselected and require an
explicit selection. Applying is not saving. Normal Save draft checks current
authorization and expected revision; a stale browser cannot overwrite another save.
Changing the form after review invalidates that review. Reimport never adds metric
rows or silently overwrites manual corrections. Each review has a UUID import batch;
observations retain sourceKind manual/csv and importId. Editing an imported metric
marks it manual while retaining the originating import ID. All remain unverified.

CSV fields: text_encoding, template_id, template_version, period_start, period_end,
timezone, channel, account, scope, metric_key, unit, state, value, source_note,
collected_at. Unit is count. Missing/non-value values require an empty value cell.
Downloads use text_encoding=apostrophe-v1 and prefix every other cell with one
apostrophe (including empty cells), so spreadsheet formulas never execute; import
removes exactly that encoding prefix. Hand-authored generic files may use plain.
No files are uploaded to a provider or retained as public assets.

Focused verification: reporting Node wildcard, reporting native-D1 harness (fresh
and populated upgrades and provenance constraints), existing reporting built-Worker
browser with CSV review/reopen/conflict cases. Full suite/build/PR checks run at the
integration checkpoint. No independent-review stop or new evidence archive per slice.

### Publication/versioning implementation decisions — 15 September 2026

The next batch uses an append-only client_report_publications ledger. A publish
entry freezes a curated snapshot of the saved draft's pinned metric definitions,
values, calculations, period, Client/Service names and explicitly client-facing
narrative. Four additive draft fields (client summary, work completed, limitations,
next actions) are private until publication. Existing Report commentary and metric
source notes/import identifiers remain internal and are never in the snapshot.
Manual and CSV inputs are visibly unverified; publishing requires explicit review
acknowledgment, saved account/scope/summary, and an existing active Client contact
membership. Publication sends no notification or mail and creates no association.

Each ledger entry has a monotonically increasing per-report sequence, authenticated
actor, timestamp and request UUID. Current draft revision and release sequence are
checked by the insertion itself. Retries reuse their entry; changed intent and
concurrent release changes conflict. Database triggers prohibit updates/deletes of
history. Withdrawal appends an entry, removing current client access while retaining
internal history; publishing a correction appends a fresh frozen version. Clients
see only the latest published entry; old/replaced/withdrawn URLs return not found.
Current membership/contact linkage is checked in every portal read. Internal access
uses the existing report Client/Service read/edit rules. Client PDF retrieval must
use that same current-version gate. Already downloaded copies cannot be recalled.

### Archive/restore decision — 16 September 2026

CLIENT_REPORTING.md requires explicit archive access rules and preserved publication
history. Archive is a reversible internal management operation, not deletion. Current
Owner/Admin/PM authority and expected draft revision are required. Archived drafts
remain readable internally under the same Client scope, are read-only, and appear
under an explicit Archived list. Portal report lists, links and PDFs deny them.

The archive write records its timestamp and the latest publication sequence as a
visibility floor in the same version-checked header update. Restore clears only the
archive timestamp: every release at or below that floor remains unavailable to the
client. A new explicit reviewed publication is required to return to the portal.
Published snapshots/history remain immutable. The saved draft, metrics and sources
are not deleted or changed. Existing creator/update metadata records the actor;
an action UUID plus fixed-order intent hash provides retry/conflict behavior. A
zero-row, failed, stale or denied update never reports a state change. Publish and
archive races are guarded by the actual saved revision. New-period reuse may use an
archived report's setup, always producing a separate private, empty draft.

## New bounded N3A decisions

- One report is for one existing Client and purchased Service engagement, one
  inclusive date range (YYYY-MM-DD, years 0100–9999), IANA timezone, one account,
  one channel and one campaign/content scope. Monthly periods are entered as their
  actual start/end dates; no aggregation, comparison or previous-period copying.
- Both templates version 1 are fixed server catalogues. Their identifiers and
  definitions are immutable; drafts pin the version. Client, Service and template
  are fixed after creation. Title, period, timezone, account/scope, commentary and
  observations remain editable with an expected revision. No provider compatibility
  is claimed. GHL channel is explicitly email or SMS; social channel is explicitly
  Facebook, Instagram, LinkedIn, TikTok, YouTube or Other. No name/slug eligibility
  inference: a manager selects the appropriate actual engagement and template.
- All entered observations are optional. Each has state value/missing/unavailable/
  not_tracked, a count, source note (up to 1000 characters), and optional collection
  instant. Counts are integers 0–1,000,000,000. Non-value states hold null, never 0.
  All numbers remain **manually entered, unverified**, even with a source note.
  A blank source is explicitly labelled. No attachments or external source fetches.
- Header identity, period/timezone and channel are required to save. Account/scope,
  metrics and commentary may be incomplete; preview marks missing context. Commentary
  is plain text up to 8000 characters. Unsupported fields and derived-value input
  are rejected. No HTML is stored or interpreted.

### Catalogue (all entered counts optional; template version 1)

| Template/key | Label and exact definition |
| --- | --- |
| ghl_campaign/sent | Sent messages: messages submitted in this report's channel, account, campaign and period; not recipient count |
| ghl_campaign/delivered | Delivered messages: the subset of those submitted messages recorded as delivered |
| ghl_campaign/failed | Failed messages: messages recorded as failed; source note must explain whether bounces are included; never added to delivered to infer sent |
| ghl_campaign/clicked | Messages with clicks: submitted messages with at least one recorded click, not total click events or unique people |
| ghl_campaign/replied | Messages with replies: submitted messages with at least one recorded reply |
| ghl_campaign/opt_outs | Opt-outs: source-recorded opt-out events in the scoped period; not inferred from replies |
| social/published | Published content: source-recorded posts/content published for this account/channel/period |
| social/views | Views: source-native view count; source note describes its definition; not reach |
| social/reach | Reach: source-native reach for the whole account/scope/period, never a sum of overlapping post reach |
| social/interactions | Interactions: source-native interaction count; definition recorded in source note; no inferred engagement rate |
| social/link_clicks | Link clicks: source-native click events, not unique people |
| social/followers_start | Followers at period start: account follower count at beginning of period |
| social/followers_end | Followers at period end: same-account follower count at end of period |

Derived (never persisted as authoritative input):
- ghl_campaign/delivery_rate: delivered / sent × 100 percent, exactly two decimal
  places, round half up using integer arithmetic. Requires both values, nonzero sent
  and nonblank account/scope. Delivered > sent rejects the save. Missing context,
  non-value input or zero denominator displays Not available. 0/positive is 0.00%.
- social/follower_change: followers_end − followers_start, signed integer people;
  requires both values and account/scope. No growth percentage. All derived output
  is labelled calculated from unverified manual inputs.
- No click/reply/engagement rate, unique cross-channel totals, revenue, leads,
  bookings or attribution calculation. These require separately defined sources.

The referenced HighLevel reports/email-widget articles were inspected for context;
these conservative manual definitions are N3A choices, not claims of exact provider
export semantics or automatic verification.
