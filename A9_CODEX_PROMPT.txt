A9 OBJECTIVE

Wire the existing Client, Service Engagements, Team assignments/setup, A8 onboarding engine, client portal invitation foundation, lifecycle, and activity into one coherent, retry-safe activation flow.

Canonical concept:

Draft Client
-> validate
-> select the Client's purchased/open Service Engagements
-> prepare deterministic onboarding through A8
-> persist exactly one onboarding instance/items/provenance/service links
-> move Client from Draft to Onboarding
-> prepare Client portal invitation for the primary contact
-> send the invitation
-> record significant activity

A9 must be safe under double-clicks, browser retries, concurrent activation attempts, mail retries, and future queue/retry duplication.

A9 OWNS

- a first-class Client activation domain operation
- activation authorization using the existing authorization engine/pattern
- precondition validation
- selecting the correct Service Engagements for activation
- orchestration with the A8 prepare/persist engine
- the Draft -> Onboarding transition
- creation/reuse/recovery of the Client-role invitation for the primary contact
- actual invitation delivery through the existing mail interface in deployed runtime
- retry behavior after mail failure
- activity for activation/onboarding/invitation facts
- minimal internal activation entry point and calm result/error UX where needed
- the Client contact portal-identity link on invitation acceptance if required by the existing A4 scope model, because client_contacts.user_id is explicitly owned by A9/A10 and A4 uses it as the durable Client-to-portal identity relationship
- tests and docs proving all of the above

A9 DOES NOT OWN

- polished Client onboarding portal UI. That is A10.
- onboarding item completion/verification UX. That is A10.
- Projects, Actions, Milestones, Deliverables, Social execution, Ads execution, Systems execution, Pages, Finance, payments, queues, or notifications beyond the one invitation delivery needed for activation

PERMANENT INVARIANTS TO PRESERVE

- BloomOps is post-sale only.
- One Client can have multiple Service Engagements.
- Departments are organizational structure, never authorization.
- owner_membership_id is operational responsibility, never authorization.
- Client assignment grants the Client plus its Services. Service assignment grants exactly that Service, not Client or siblings.
- A Client's relationship status, Client health, Service status, onboarding status, Project status, and Action status remain separate facts.
- activity is append-only.
- no raw platform passwords.
- environments remain isolated.
- A8 template definitions/provenance are immutable snapshots, while generated runtime onboarding records remain operationally mutable.
- master template changes never silently rewrite an existing generated onboarding instance.
- same-workspace foreign-key protections must remain intact.

ACTIVATION AUTHORIZATION

Use the existing server-side authorization model. Do not make UI visibility equal authorization.

Prefer a distinct internal action such as client.activate if that fits the existing action registry and tests. Follow existing action naming and role/capability conventions rather than adding role checks ad hoc.

Activation must never be available to Client-role users. It must remain workspace-scoped and Client-scoped. A caller handed a foreign Client id must receive the same safe not-found/denied semantics used elsewhere.

Do not widen access because someone is in a Department or is owner_membership_id.

ACTIVATABLE STATE

The canonical first activation transition is Draft -> Onboarding.

A fresh activation request against a Draft Client may proceed if all required validation passes.

A request against a Client that has already completed the A9 core activation must be handled idempotently. It must not create another onboarding instance, duplicate activation activity, duplicate the lifecycle transition, or duplicate core business records.

Do not treat an arbitrary non-Draft lifecycle as permission to activate. Active, Paused, Completed, or Ended should not be silently rewritten to Onboarding.

If the implementation needs to distinguish a legitimate prior A9 activation from an unrelated impossible/legacy state, use durable relational facts and existing invariants. Do not use client-supplied flags. Do not make append-only activity the only database authority if a stronger relational invariant is available.

CORE CONSISTENCY AND IDEMPOTENCY

Design for retries first, not as an afterthought.

The durable core facts are:
- exactly one open onboarding instance per Client, enforced by the database
- exact A8 provenance and item/service links
- Client lifecycle reaches Onboarding exactly once for initial activation
- activation activity is not duplicated

The database must remain the final concurrency authority.

Two concurrent first activations must converge to one valid activated Client, one open onboarding instance, one set of generated onboarding rows, and one set of core activation activity. The loser must receive a safe idempotent/conflict result, never a raw constraint error.

Do not use a check-then-insert sequence as the only protection.

Where one fact and its activity must be inseparable, use the established db.batch/transaction pattern so a late DB failure cannot leave a lifecycle change without its corresponding core activity, or vice versa.

Do not fake atomicity in the test double. If the implementation extends batch behavior, keep BEGIN/COMMIT/ROLLBACK semantics consistent with actual D1.

INVITATION AND MAIL BOUNDARY

Reuse the existing invitation token, hash, TTL, Client-role invitation, acceptance, and mail infrastructure. Do not invent another token system.

The activation invitation targets the current primary contact:
- role = client
- clientId = activated Client
- email = normalized primary contact email
- inviteeName from that contact when appropriate
- invitedByMembershipId = authenticated activating actor when the existing invitation model expects it

Raw invitation tokens must never be stored in the database or logged.

External email is not part of a D1 transaction. Structure the flow so a mail failure cannot cause core activation records to be duplicated or rolled back into an ambiguous half-state.

Required retry behavior:
- if core activation commits and invitation delivery fails, return a structured result that makes clear activation succeeded but mail failed
- preserve enough durable invitation state to retry safely
- a retry must not create another onboarding instance or another Draft -> Onboarding transition
- a retry may create/rotate/reuse the pending invitation according to the existing invitation semantics, then attempt delivery again
- if rotation is required because only a token hash is stored, the new valid token may supersede the previous pending token. Do not expose the raw token anywhere except the immediate send path
- do not create repeated CLIENT_ACTIVATED or ONBOARDING_STARTED events just because mail is retried
- invitation-specific resend/sent activity may follow the existing invitation semantics, but avoid duplicate facts for one successful operation

Do not call a real Resend endpoint in unit/integration tests. Inject/stub the mailer/fetch using the existing mail interface.

INVITATION ACCEPTANCE AND CLIENT CONTACT LINK

The current domain explicitly states client_contacts.user_id is the durable relationship A4 uses to decide which Client a Client membership may see, and that A9/A10 own inviting, accepting, linking, and later unlinking.

Implement the minimum correct A9 linkage needed so an invited primary Client contact who accepts can actually be scoped to that Client later.

Requirements:
- only for Client-role invitations with a clientId
- the accepting signed-in user's email must already satisfy the existing invitation email check
- link the intended Client contact, not a random same-email contact from another Client/workspace
- prefer the primary contact that activation invited, with a durable association if needed so acceptance cannot drift after contact edits
- never let a foreign workspace invitation link a local contact
- linking must be idempotent for the same user/contact
- conflicting attempts to link one contact to a different user, or one Client-role membership to an unintended Client, must fail safely
- do not expose user ids in internal UI payloads beyond the existing boolean linked fact
- do not silently infer portal access from email alone outside the invitation acceptance path

If the current schema cannot unambiguously preserve which contact was invited between activation and acceptance, add the smallest relational field/junction needed with same-workspace constraints and a migration. Do not hide this association in JSON metadata.
