PRIMARY PRODUCT CONTRACT

Milestones are ordered child records of one Project. They are not a duplicate Project lifecycle.

Use the canonical B2 states exactly:
- upcoming
- in_progress
- waiting
- completed
- skipped

Use the lifecycle from docs/phases/B2.md:
- upcoming -> in_progress | waiting | skipped
- in_progress -> waiting | completed | skipped
- waiting -> in_progress | completed | skipped
- completed terminal
- skipped terminal

Every Milestone starts upcoming. Completion timestamps are server-owned. Identical retries are no-ops. Stale competing writes return conflict. Do not let request bodies directly write arbitrary status/completed timestamps/parent/workspace facts.

A Milestone belongs to one workspace and one Project. Client, Service, and Department context derive from the parent Project. Do not duplicate them as independent Milestone lifecycle facts.

Likely fields, unless current repository evidence strongly supports a smaller equivalent:
- id
- workspace_id
- project_id
- name
- client_label nullable
- status
- position
- start_date nullable
- target_date nullable
- completed_at nullable
- visibility
- revision or equivalent concurrency token
- created_at
- updated_at

Use an additive Drizzle migration after B1, expected 0009_b2_milestones.sql unless the journal requires an exact adjacent name. Add matching Drizzle snapshot/journal state. Do not rebuild Release A or B1 tables.

AUTHORIZATION / VISIBILITY

Preserve the existing Identity -> Role -> Scope -> Visibility model.

Add explicit milestone actions only as needed, likely milestone.view and milestone.manage. Do not add roles.

Owner/Admin/Project Manager may coordinate reachable Milestones. Team Member remains read-only.

A Team Member reaches a Milestone only through the EXISTING parent Project scope rules:
- client assignment grants ordinary Projects under that Client
- service assignment grants Projects under that Service
- explicit project assignment grants only that Project
- department membership grants nothing
- Project ownership grants nothing

A child Milestone must never broaden scope to the parent Client, Service, sibling Project, or sibling Milestone outside the readable Project.

Parent Project visibility caps Milestone visibility. Portal requires BOTH parent Project visibility=client and Milestone visibility=client plus the current client_contacts.user_id relationship. Internal/restricted parent means no Client child visibility.

For restricted Milestones, preserve B1 restricted behavior: Owner/Admin can see; Project Manager/Team Member require the explicit Project assignment used for restricted Project access. Client never sees restricted work.

All guessed/foreign/cross-workspace/cross-client/cross-project IDs must fail leak-safely.

Do not serialize raw Milestone rows to portal code. Build a dedicated exact allowlist projection.

ORDERING

Implement deterministic per-Project order with the smallest safe relational approach.

Requirements:
- Project A reorder cannot affect Project B
- foreign/guessed IDs cannot enter an order operation
- malformed duplicate/missing IDs are rejected where the operation expects a complete set
- winning reorder and semantic activity are atomic
- concurrent/stale reorders cannot silently lose updates
- retry of the winning order is a no-op with no duplicate event
- reads remain deterministic even if storage permits temporary equal positions

Do not add a second Project-status fact merely to coordinate ordering. If you add a separate ordering revision/token, justify it as concurrency metadata only and test it thoroughly. Prefer a Milestone-local/relational solution if it stays correct.

PROGRESS

Progress is derived, never persisted as a second status.

Internal Project progress summarizes currently readable Milestones. Client progress uses only client-visible Milestones under a client-visible parent Project.

Completed + Skipped count as terminal/finished for progress math. Use wording like finished, not completed, when skipped rows are included.

If zero visible Milestones exist, do not fabricate 0% or render an empty progress module.

Hidden/restricted Milestones must not affect Client counts, percentages, labels, or whether a progress section exists.

ACTIVITY

Use canonical activity_events with subject_type='milestone'. Carry Client/Service context derived from the Project.

At minimum distinct semantic events for:
- MILESTONE_CREATED
- MILESTONE_DETAILS_UPDATED
- MILESTONE_STATUS_CHANGED
- MILESTONE_ORDER_CHANGED or an equivalently clear reorder event

Mutation and event must share one transaction/batch. A late activity failure must roll back the Milestone fact. Retries/concurrent losers cannot duplicate history.

If Project activity includes Milestone child events, filter them by CURRENT Milestone readability and current Project visibility so an event created while visible cannot leak after restriction. Clients receive no internal Milestone activity in B2.
