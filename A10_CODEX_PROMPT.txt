IMPORTANT CURRENT TEMPLATE SEMANTICS

The committed A8 schema-v1 onboarding definition has:
- logicalKey
- title
- instructions
- required
- verificationRequired
- responsibleParty
- visibility
- position

It does NOT have an interaction/input type, upload flag, URL field, or form schema.

Current default runtime requirements are client-visible/client-responsible. Examples include Agreement, Brand assets, Kickoff booking, Instagram access, Meta Business access, GHL access, Kajabi access, and optional Course videos. Access items are verification-required where configured.

Do not infer an interaction type from logicalKey/title/instructions.
Do not invent URLs from text.
Do not treat a title containing “assets” or “videos” as permission to build a file uploader.
Do not mutate immutable A8 template definitions or silently rewrite existing generated runtime snapshots.

The A10 phase file says file upload is conditional (“If Release A file upload is included here…”). Release A acceptance does not require a general onboarding upload system, and schema-v1 cannot explicitly express which item expects an upload. Therefore onboarding file upload is NOT an A10 acceptance requirement for this implementation. A client may acknowledge/submit that they completed an externally described step. Keep the boundary explicit in docs. Do not claim the Files module exists.

Likewise, do not fabricate an external link for Kickoff booking because schema-v1 carries no URL.

PORTAL READ MODEL AND PRIVACY

Build a dedicated server-side read model for portal onboarding. Do not hand raw onboarding rows to Client UI.

For a Client actor:
- derive reachable Client ids from the existing A4 contact scope
- use the A9 activation’s onboarding instance where applicable
- include only items whose visibility is exactly client
- never expose internal/restricted items
- never expose another Client’s items even if an item/instance id is guessed
- do not expose template version ids, provenance internals, internal membership ids, actor ids, hidden service ids, internal notes, raw invitation data, or other implementation-only fields
- do not use email matching as portal authorization. A9’s client_contacts.user_id link remains the durable authority

Public item projection should contain only what the Client needs, such as:
- id
- title
- instructions
- required / optional
- verification-required fact if useful for UX
- client-facing state
- position/order
- timestamps that are safe and useful
- whether the Client can act now

Do not expose logical keys unless there is a real client-facing need. They are implementation identity, not UI copy.

MULTI-CLIENT SAFETY

The existing A4 model can technically scope a Client membership to a set of linked clients. Do not assume clients[0] is always the only possible client.

If one account has one linked Client, the portal can naturally focus on that Client.
If it has multiple reachable Clients, render or select them in a way that preserves per-client isolation and makes the current Client context explicit.
Do not create a route where changing clientId bypasses actor scope.

CLIENT-FACING PROGRESS

Do not leak hidden internal work through progress denominators.

Use a client-facing “your steps” progress based only on client-visible, client-responsible required items.

A Client has done their part for a required item when:
- status is Completed, Waived, or Not Applicable; OR
- verificationRequired is true and the Client has durably submitted it for verification

That means a Client may reach 100% of “your steps” while overall onboarding is still waiting for internal verification or other agency work. In that state the UI should say something like “You’re all set for now. We’re checking the remaining steps.” Do not reveal how many hidden internal items remain.

Optional items must be visibly optional and must never block onboarding completion.

For client-visible items owned by Team/Specific User/External, show calm read-only status if they are client-visible, but do not give the Client a completion control.

Suggested client-facing states, derived from durable data rather than stored display strings:
- To do
- Waiting for us / Awaiting verification
- Complete
- No action needed
- We’re handling this

Keep status semantics grounded in the canonical item states: Pending, In Progress, Completed, Blocked, Waived, Not Applicable.

DURABLE SUBMISSION / VERIFICATION STATE

Existing onboarding_items has verificationRequired, status, completedAt/by, verifiedAt/by, but no unambiguous durable “client submitted this and is waiting for verification” actor/timestamp.

Add the smallest correct relational runtime state needed to represent submission without changing A8 template-definition semantics.

Requirements:
- submission must be durable
- submission actor must be attributable to the Client membership/user through same-workspace relational constraints where practical
- retrying the same submission must be idempotent
- a verification-required item must not become Completed merely because the Client clicks submit
- the team must be able to distinguish untouched In Progress from actual awaiting verification
- no raw payload/secrets are stored

Choose the cleanest additive schema shape. A small relation such as onboarding_item_submissions is acceptable if it avoids unsafe table rebuilds. If you add columns instead, preserve migration safety and same-workspace guarantees. Do not use activity history as the only authority for current submission state if a stronger relational fact is practical.

CLIENT ITEM MUTATION

Provide a server-authorized client action/API. Do not accept arbitrary status from the request body.

A Client may act only when all are true:
- authenticated active Client membership in active workspace
- item belongs to an onboarding instance for a Client in the actor’s A4 contact scope
- item.visibility = client
- item.responsibleParty = client
- item is in a state where the requested Release A action is valid

For a non-verification-required Client item:
- Client “complete / I did this” moves it to Completed
- completedAt/by are recorded
- activity is recorded atomically
- retry is a no-op/idempotent result, not duplicate activity

For a verification-required Client item:
- Client action means submit/confirm that access was sent
- persist durable submission actor/time
- item becomes/remains In Progress, not Completed
- UI becomes Awaiting verification
- completion/verified fields stay unset until internal verification
- repeated submit is idempotent

Do not add Client-side reopen/undo in Release A unless a canonical requirement demands it. Prefer monotonic safe transitions.

FIRST PROGRESS MUTATION

If onboarding instance status is Not Started, the first real item progress mutation should move it to In Progress and set startedAt atomically. Merely viewing the portal should not count as starting work.

Turn the existing internal Client > Onboarding tab into the minimum useful operational surface.

It should show, for the selected Client only:
- onboarding instance state
- progress/status summary
- ordered items
- required/optional
- responsible party

- whether verification is required
- whether a Client submission is waiting
- current item status
- safe action controls for authorized internal users

Use server-side authorization. UI visibility is not authorization.

Prefer distinct onboarding actions in the A4 registry if that keeps policy explicit, for example onboarding.submit / onboarding.verify / onboarding.manage. Follow repository naming patterns.

Internal verification/management should be available to the roles current Release A defines as delivery coordinators (Owner/Admin/Project Manager) unless existing canonical policy clearly supports a narrower/broader set. Do not widen power because of Department membership or owner_membership_id. Team Member assignment alone should not magically gain a new write unless you deliberately add/test a scoped onboarding action that canonical docs support.

VERIFICATION REQUIRED FLOW

For verificationRequired client items:

Client submits
-> durable submission exists
-> item is In Progress / Awaiting verification
-> authorized internal user verifies
-> item becomes Completed
-> verifiedAt/by are set
-> completedAt/by are set consistently
-> verification activity is appended

Internal verify before Client submission must fail safely.
A Client can never self-verify.
A foreign/internal user outside scope can never verify by guessing item ids.
Two concurrent verifies must converge to one completion and one semantic event.

INTERNAL COMPLETION FOR OTHER ITEMS

Custom templates may contain Team / Specific User / External responsibilities even though current defaults are client-owned.

Authorized internal users need a minimal way to mark appropriate non-client work Completed so Release A completion logic is not hard-coded only for current defaults.

Do not let the Client complete these items.
Do not invent assignment grants. Scope through the Client/resource and existing authorization model.

WAIVED / NOT APPLICABLE

A11 explicitly requires proving that a waived required item leaves an audit trail, so A10 must provide the underlying Release A capability.

Authorized internal users may resolve an item as:
- Waived
- Not Applicable

Requirements:
- a non-empty bounded reason is mandatory
- the reason is durable and queryable
- append-only activity records the resolution and reason
- Client cannot waive or mark N/A
- the resulting status satisfies completion for a required item
- retries must not duplicate activity
- do not silently overwrite one terminal resolution with another
- internal UI should make the reason visible to authorized internal users; expose it to Client only if deliberately safe/necessary, otherwise show “No action needed” without internal rationale

Use the smallest correct relational shape. Activity metadata can be part of the audit trail, but do not create a state whose reason disappears from operational inspection.

COMPLETION RULE

Overall onboarding completion is server-owned and must evaluate ALL required onboarding items for the instance, regardless of visibility or responsible party.

An item satisfies the required completion rule only when its canonical status is:
- completed
- waived
- not_applicable

A verification-required item that is merely submitted/in_progress does NOT satisfy overall completion.

Optional items never block completion.

Do not compute overall completion from the client-facing progress projection.

ONBOARDING INSTANCE LIFECYCLE

On any item transition that could satisfy the final outstanding requirement, re-evaluate completion under the same database write/transaction authority.

When every required item is satisfied:
- onboarding_instances.status -> complete
- completedAt is set
- completedByMembershipId identifies the actor whose valid mutation caused completion where meaningful
- ONBOARDING_COMPLETED activity is appended exactly once

Before complete, use canonical instance states honestly. It is acceptable to use Not Started -> In Progress -> Complete for Release A if Ready/Blocked do not have a defined transition in current implementation. Do not manufacture Ready/Blocked semantics just to use every enum value.

CLIENT LIFECYCLE ON COMPLETION

Release A acceptance requires the Client to become Active after onboarding completes.

Canonical automatic transition for this phase:
- if Client relationship status is still onboarding when the initial onboarding instance completes, move it to active atomically with completion
- append a distinct meaningful Client lifecycle activity exactly once

Do not rewrite Draft, Paused, Completed, Ended, or another unexpected lifecycle to Active merely because an onboarding item changed.
If the Client is already Active, completion should remain idempotent and not duplicate lifecycle activity.
Do not mutate Service status as a side effect. Client, Service, and Onboarding lifecycles remain separate facts.

ATOMICITY / CONCURRENCY

The database is the final authority.

Design and test these races:
- two Client clicks on the same non-verification item
- two Client submissions on the same verification item
- Client submission racing an internal verify
- two internal verifies
- two final-item mutations that could both observe “one remaining”
- retry after response loss
- late activity insert failure

Required result:
- one durable item transition
- one semantic activity fact
- one onboarding completion
- one Client Onboarding -> Active transition
- no raw unique/check/FK errors in HTTP responses
- no partial item state without its corresponding activity when the activity is defined as inseparable

Use db.batch/transaction patterns already established in A6-A9. Do not fake transaction behavior in the test double.

ACTIVITY

- onboarding item submitted by Client
