Do not implement Action dependency mechanics in B1.

PROJECT RELATIONSHIPS

Every Project belongs to one workspace and one Client.

Service Engagement:
- may be nullable for legitimate Client-level Projects
- if provided, it must belong to the same workspace and Client
- never infer a Service by name or Department

Department:
- organizational metadata only
- must never grant authorization
- if the Project has a Service Engagement whose Service Type already carries a Department, prefer a coherent validated relationship rather than duplicating contradictory Department truth
- do not permit a Project to claim a Department inconsistent with its linked Service without an explicit canonical reason

Responsibility / ownership:
- an optional Project owner/responsible membership may be used for coordination
- it must be an active or otherwise canonically valid internal workspace membership
- never use owner field as an authorization bypass

PROJECT ASSIGNMENTS

B1 should support an explicit Project assignment relation if needed to make Team Member scope canonical.

Requirements:
- workspace-scoped relational FKs
- Project and member must share workspace
- no Department-wide access grant
- no duplicate assignment rows for the same Project/member
- assignment is responsibility/scope, not a new role
- Owner/Admin/Project Manager retain delivery coordination scope
- Team Member can reach a Project only through an already-supported broader Client/Service assignment OR explicit Project assignment according to the authorization design you establish and test

Be conservative about widening Team Member access. Prefer additive explicit scope over implicit grants.

PROJECT LIFECYCLE

Implement explicit server-owned transitions. Do not accept arbitrary status assignment from request bodies.

Define a transition matrix grounded in the canonical Project lifecycle.

At minimum support sensible movement through:
planned -> ready -> in_progress
in_progress <-> waiting / blocked / review where operationally valid
review -> in_progress or completed
completed -> archived
cancelled -> archived

Do not assume this exact matrix if existing Product/Domain rules require a correction; document the final matrix in DOMAIN_MODEL.md.

Requirements:
- invalid transitions fail safely
- status update and semantic activity are atomic
- completedAt is set only on transition into completed and retained appropriately
- leaving completed should not be allowed unless the canonical lifecycle explicitly supports reopening; B1 may make completed monotonic except archive
- cancelled and archived must not silently return to active work states
- status retry after response loss is idempotent
- concurrent identical transitions yield one stored transition and one semantic activity event
- competing transitions cannot create contradictory event history

Project status must NOT mutate Client status or Service status.
