CONTEXT

PR #10 (A8) was independently audited and merged cleanly. Post-merge staging deployment run 34078492009 succeeded on main SHA adcdec226f75b81969d510ac21a4d772a1cf5371.

Post-merge zero-to-current run 34078492054 failed, but the disposable migration verification itself passed completely. The failure happened only in cleanup after the verifier had already reported:
  zero-to-current verification passed

Exact observed sequence from the failed run:
- bloomops-staging had 58 tables when the zero verifier started.
- the verifier created and used only disposable DB bloomops-a2-zero-verify.
- all 60 inherited migrations and all 6 BloomOps domain migrations applied successfully.
- all 23 BloomOps domain tables existed.
- all migration-defined triggers existed.
- all migration-defined indexes existed.
- second pass applied nothing and the disposable schema/ledgers were identical.
- disposable DB was deleted successfully.
- account database inventory returned exactly to the original set.
- meanwhile the independent Deploy staging workflow legitimately applied A8 migration 0005 to bloomops-staging, increasing staging from 58 to 59 tables.
- cleanup then failed `bloomops-staging untouched` because verify-zero-remote.mjs requires stagingAfter.num_tables === stagingBefore.num_tables.

The current final cleanup assertion is therefore race-prone. It treats any legitimate concurrent staging migration as proof that the zero verifier touched staging, even though this verifier structurally cannot target staging because every database command uses a temporary config bound only to the disposable DB and guard() refuses protected targets.

OBJECTIVE

Fix the zero-to-current verifier so it still proves isolation from staging/production without failing merely because another legitimate workflow changes staging concurrently.

REQUIRED BEHAVIOR

1. Preserve all current safety guards:
   - disposable DB name cannot collide with staging/production/Leadsthatbloom/Bloomwired protected names
   - committed staging and production IDs must be known/distinct
   - created disposable DB ID must differ from staging/production IDs
   - database commands must continue using the temporary wrangler config bound only to the disposable DB
   - guard() must continue refusing commands that could target protected resources
   - account inventory before/after must return exactly to the original database set after disposable cleanup
   - disposable DB identity must be checked before deletion

2. Remove or redesign only the invalid assumption that staging metadata must remain byte-for-byte/static throughout the whole verifier run.

3. A legitimate concurrent staging deployment must not make this workflow red.

4. Do not weaken isolation into a meaningless check. The verifier should still demonstrate that this script addressed only the disposable database. A good direction is:
   - keep structural command/config guards as the primary authority
   - if reading staging before/after remains useful, compare stable identity such as UUID/created_at, and treat mutable schema/table-count changes as informational rather than evidence that this verifier wrote staging
   - or use another equally strong race-safe proof

5. Do not serialize or cancel unrelated staging deployment unless there is a compelling reason. Prefer making the verifier's proof correct under concurrency instead of hiding the race with workflow ordering.

6. Do not touch production, DNS, staging data manually, or Leadsthatbloom.

7. Do not change A8 runtime/domain behavior, migration 0005, template engine behavior, or application code unless genuinely required. This should be a small verifier/workflow/test/docs correction.
